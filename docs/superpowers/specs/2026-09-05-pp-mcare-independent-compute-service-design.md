# pp-mcare 独立动作分析计算服务设计

## 1. 背景

MotionCare 已经具备训练视频上传、七牛云私有存储、`TrainingVideo`、`MotionAnalysisJob`、医生端视频查看以及 PP-TinyPose 肩部推举全帧计数 v2。当前动作分析仍由业务后端的 Celery 任务执行，并由医生手动创建任务；独立算法服务器只完成了离线冒烟和真实视频验收，尚未进入业务闭环。

本设计把 `pp-mcare` 建设为独立计算服务。它与 MotionCare 位于同一个 Git 仓库，但拥有独立依赖、构建产物和部署流程，运行在另一台服务器。两者只通过受控 HTTPS API 通信；算法服务器不连接业务数据库、Redis 或 Celery，也不持有七牛云 AK/SK。

现有训练视频分片、业务服务器合并、上传七牛并创建 `TrainingRecord` 的链路保持不变。本设计从 `TrainingVideo` 已达到 `attached` 且已经绑定训练记录之后开始。

## 2. 已确认决策

1. 原视频在七牛云可用并绑定训练记录后，由 MotionCare 自动创建动作分析任务；医生端取消开始分析和重新分析按钮。
2. `pp-mcare` 主动轮询 MotionCare，不开放业务入站端口，不共享数据库、Redis 或 Celery。
3. 空队列轮询间隔固定为 15 分钟；启动时立即轮询，有任务时完成一项后立即领取下一项。
4. 每次只领取和执行一个任务，使用租约与心跳维持所有权，整条业务链路严格串行。
5. MotionCare 为每项任务签发原视频短期下载 URL，以及只允许上传到指定骨架对象键的七牛云短期上传凭证。
6. PP-TinyPose 对视频原始全部帧执行一次流式推理，不保留 5 FPS、10 FPS 或其它抽帧生产入口。
7. 只锁定、分析并绘制主训练者。画面中的其他人员不参与计数，也不出现在骨架视频中。
8. 复用 PP 的骨架可视化组件；先过滤为单个主训练者，再绘制该人的关键点，不直接输出 PP 原始多人可视化结果。
9. 骨架视频不叠加动作次数、阶段、标准性或质量文案，不保留原视频音轨。
10. 一个基础 PP 环境承载下载、推理、可视化、编码、上传和清理；每个动作通过 `source_key` 映射到独立规则插件。
11. 算法与医生都写 `TrainingRecord` 上同一组动作结果字段。医生可覆盖算法结果；未来若新增算法重试，新的成功结果也覆盖这些字段。
12. `MotionAnalysisJob` 保留任务状态、算法原始输出、版本、失败原因和骨架视频元数据，用于排错；它不是医生日常修改的业务结果来源。
13. 当前版本不提供成功任务重新分析，也不重新运行已经失败的动作算法。失败后医生直接填写训练结果。
14. 同一次执行中的下载、上传和 API 回传可以进行有限的技术重试；技术重试不创建新任务，也不重新执行已经失败的算法。
15. 成功或失败后清理算法服务器本地输入、输出和中间文件；模型缓存、应用环境和脱敏运行日志可以保留。
16. 代码统一放在 MotionCare 仓库，MotionCare 与 `pp-mcare` 分别构建并部署到不同服务器。

## 3. 目标与非目标

### 3.1 目标

- 建立训练视频从自动排队到动作分析、骨架视频、训练结果回写的完整闭环。
- 让算法计算与业务数据库、消息队列和七牛云长期凭证隔离。
- 保持单并发、低任务量场景下的实现和运维简单性。
- 通过动作插件扩展新的运动动作，而不复制视频下载、PP 推理、编码和上传代码。
- 让医生对照原视频和骨架视频，并可直接修正当前训练结果。
- 保留足够的任务、算法版本和原始输出信息，以便定位问题和验证算法变化。

### 3.2 非目标

- 不做实时摄像头推理或患者训练中的实时纠错。
- 不提供多任务并发、批量租约或多服务器调度。
- 不提供医生端或管理端重新分析按钮。
- 不对失败的算法任务自动重跑或人工重投。
- 不建设模型训练、标注或在线阈值调参平台。
- 不给骨架视频保留音轨或增加动作分析文字水印。
- 不改变小程序分片录像、业务服务器合并和原视频上传七牛的既有链路。

## 4. 方案选择

采用“算法服务器主动轮询 + 单任务租约 + 短期对象存储权限”。

未采用的方案：

- **MotionCare 主动调用算法服务器**：任务启动可能更及时，但算法服务器需要开放入站接口，并增加回调超时、防火墙和公网鉴权复杂度。
- **共享 Redis/Celery 或 PostgreSQL**：可复用现有任务代码，但会把业务基础设施和数据库权限扩展到算法服务器，故障与安全边界不清晰。
- **一次领取一批任务**：能减少领取请求，但未执行任务会被长时间占有；服务重启时需要回收整批租约。空队列 15 分钟轮询、积压时连续领取，已经能把空请求控制在每天最多 96 次，同时只锁定当前执行项。

## 5. 代码与部署边界

建议目录边界：

```text
MotionCare/
├── backend/                         # Django 业务服务、数据库模型、内部任务 API
├── services/
│   └── pp_mcare/                    # 独立算法 worker、PP 适配器、流水线和动作插件
└── packages/
    └── motion_analysis_contract/    # 不依赖 Django/Paddle 的纯协议对象与校验规则
```

`backend` 与 `services/pp_mcare` 分别管理依赖和启动入口。部署 `pp-mcare` 时只打包算法服务及纯协议包，不打包 Django 应用；部署业务端时不安装 PaddlePaddle、PaddleX 或 OpenCV 推理依赖。

纯协议包只定义领取任务、心跳、完成、失败和结果负载的数据结构，不包含数据库模型、对象存储客户端或算法逻辑。双方通过契约测试保证协议兼容。

首版延续已经验收的 Ubuntu 24.04、Python 3.12、CPU 原生虚拟环境，以 systemd 运行单个常驻 worker。`pp-mcare` 不监听业务端口，只发起到 MotionCare 和七牛云的出站 HTTPS 请求。

## 6. 总体数据流

```text
小程序分片录像
  -> MotionCare 合并完整视频并上传七牛
  -> 创建 TrainingRecord，TrainingVideo 进入 attached
  -> 同一业务事务幂等创建 MotionAnalysisJob(pending)

pp-mcare 启动或空队列等待 15 分钟后
  -> 携带自身能力列表向 MotionCare claim
  -> MotionCare 原子领取最早且受支持的 pending 任务
  -> 返回租约、动作快照、短期原视频 URL、限定骨架对象键的上传凭证
  -> pp-mcare 下载并校验视频
  -> 全帧 PP-TinyPose + 主训练者追踪
  -> 同一份单人关键点流进入动作插件和 PP 可视化
  -> 编码无声骨架 MP4并校验
  -> 上传七牛指定对象键
  -> complete 回传结构化结果和骨架元数据
  -> MotionCare 校验七牛对象
  -> 数据库事务完成任务并覆盖 TrainingRecord 当前动作结果
  -> pp-mcare 收到成功确认后清理任务目录
  -> 立即 claim 下一项；队列为空时再等待 15 分钟
```

若处方动作没有注册自动分析能力，MotionCare 不创建任务；医生端显示“暂不支持自动分析”，并允许医生直接填写结果字段。

## 7. 数据模型

### 7.1 TrainingRecord 当前动作结果

`TrainingRecord` 新增当前有效动作结果字段：

```text
motion_total_count                 nullable positive integer
motion_standard_count              nullable positive integer
motion_nonstandard_count           nullable positive integer
motion_quality_data                JSON, default {}
motion_result_source               blank | algorithm | doctor
motion_result_updated_by           nullable User
motion_result_updated_at           nullable datetime
```

约束与写入规则：

- 三个计数字段要么全部为空，要么全部为非负整数。
- 非空时必须满足 `motion_total_count = motion_standard_count + motion_nonstandard_count`。
- 算法成功时在完成任务的同一事务中覆盖这些字段，来源为 `algorithm`，修改人为 `null`。
- 医生保存时写相同字段，来源改为 `doctor`，记录当前医生和时间。
- `motion_quality_data` 保存当前对业务有意义的质量摘要；逐帧或逐次算法诊断仍保留在任务原始输出中。
- 跟踪、列表、导出和医生端展示均直接读取这些字段，不再通过“最新成功任务”推导当前值。

医生编辑不会改写已经完成的 `MotionAnalysisJob`。这样当前业务值保持单一来源，原始算法证据仍可用于排错。

### 7.2 MotionAnalysisJob

沿用现有任务模型和 `pending | running | succeeded | failed` 状态，新增或调整以下信息：

```text
worker_id
lease_token_hash
lease_expires_at
last_heartbeat_at
action_source_key
algorithm_name / algorithm_version
rule_version / parameter_version
subject_tracker_version
total_count / standard_count / nonstandard_count
result_payload
failure_code / failure_reason
skeleton_bucket / skeleton_object_key / skeleton_object_hash
skeleton_size_bytes / skeleton_duration_seconds
skeleton_width / skeleton_height / skeleton_fps
started_at / finished_at
```

任务创建时生成不可变的骨架对象键，建议格式：

```text
motion-analysis/{project_patient_id}/{yyyy}/{mm}/{job_uuid}/skeleton.mp4
```

同一视频当前只由自动绑定流程创建一次任务。重复完成视频绑定必须返回既有任务，失败后也不得因重复回调创建新任务。为未来重新分析保留一对多任务关系，但本期没有创建第二项任务的入口。

骨架视频跟随训练视频生命周期。删除训练视频或患者解绑导致视频清理时，原视频和全部骨架对象都通过现有七牛清理墓碑机制删除；数据库事务不等待远端删除完成。

## 8. 自动建任务与能力匹配

当 `TrainingVideo` 与 `TrainingRecord` 绑定并进入 `attached` 时，业务服务在同一数据库事务内执行幂等任务创建，避免训练记录已经可见但分析任务丢失。

MotionCare 保存允许自动建任务的 `source_key` 清单。`pp-mcare` 在领取请求中声明当前部署实际支持的动作、规则版本和协议版本。业务端只把动作与能力都匹配的任务交给该 worker；版本不兼容时不领取，并记录可运维诊断的原因。

首版只要求已经验收的：

```text
motion-resistance-shoulder-press -> shoulder_press_v2
```

后续新增动作时，需要新增独立插件、测试样本和动作支持配置，不修改基础流水线。

## 9. 内部 API 契约

内部接口统一位于 `/api/internal/motion-analysis/`，使用独立机器凭证鉴权，不使用医生 Session。

### 9.1 领取任务

```text
POST /api/internal/motion-analysis/jobs/claim/
```

请求包含 `worker_id`、协议版本和动作能力列表。业务端使用数据库行锁原子选取最早的匹配任务，将其置为 `running`，生成一次性租约令牌并返回：

- job ID、动作 `source_key` 与处方动作快照；
- 算法、规则和参数版本要求；
- 租约到期时间和心跳间隔；
- 原视频元数据与短期私有下载 URL；
- 已固定对象键的七牛上传凭证；
- 完成接口要求的结果协议版本。

默认租约有效期为 5 分钟，worker 每 60 秒发送一次心跳并续回完整 5 分钟；这两个值由业务端返回，worker 不自行猜测。原视频下载 URL 默认有效 60 分钟，限定对象键的上传凭证默认有效 3 小时，可以覆盖当前 60 分钟最长视频约 74 分钟的实测推理时间和上传余量。凭证过期后不提供刷新接口，本次任务按存储凭证失败收口，避免引入跨租约的长期权限。

无任务返回 `204 No Content`。worker 等待 15 分钟后再次请求；启动、成功或失败收口后立即请求，不等待 15 分钟。claim 的短暂网络错误先执行最多 3 次递增退避，仍失败后再等待 15 分钟。

### 9.2 心跳

```text
POST /api/internal/motion-analysis/jobs/{job_id}/heartbeat/
```

请求携带租约令牌和当前阶段。合法心跳延长当前任务租约。令牌不匹配、任务已终态或租约已经过期时拒绝续约。

### 9.3 完成

```text
POST /api/internal/motion-analysis/jobs/{job_id}/complete/
```

请求包含幂等键、租约令牌、版本、三项计数、质量摘要、原始结果负载和骨架视频元数据。MotionCare 必须：

1. 校验租约、协议和任务状态；
2. 校验三项计数的类型与守恒关系；
3. 校验骨架对象键与任务预分配键完全一致；
4. 通过七牛对象查询确认对象存在，且 hash、大小、内容类型符合回传值；
5. 在一个数据库事务内保存任务原始结果、置为 `succeeded`，并覆盖训练记录当前动作结果；
6. 对相同幂等键的重复完成请求返回相同成功结果，不重复写业务数据。

### 9.4 失败

```text
POST /api/internal/motion-analysis/jobs/{job_id}/fail/
```

请求包含幂等键、租约令牌、稳定失败代码、脱敏摘要和阶段耗时。合法请求把任务置为 `failed`，不创建新任务，不清空医生已经填写的训练结果。

业务服务器定时扫描租约超时任务并标记 `failed`，同样不重新排队。公开医生接口只返回安全失败文案，不返回 traceback、文件路径、令牌或签名 URL。

## 10. pp-mcare 流水线

每个任务使用权限为 `0700` 的独立临时目录，按以下阶段串行执行：

1. **领取与预检**：校验协议、动作插件、剩余磁盘和可用内存。
2. **下载**：使用短期 URL 流式下载到临时文件，校验大小、容器和可解码视频流。
3. **全帧推理**：逐帧解码，每个成功解码帧恰好执行一次 PP-TinyPose。
4. **主训练者锁定**：从多人检测结果中建立并跨帧维持唯一主训练者身份。
5. **双路消费**：过滤后的单人关键点同时进入动作插件和 PP 骨架可视化，不执行第二次推理。
6. **编码**：按原视频时间轴编码 H.264、`yuv420p`、`faststart` 的无声 MP4。
7. **输出校验**：确认视频可解码、帧数合理，且与原视频时长偏差不超过 `max(1 秒, 原时长 1%)`。
8. **上传与校验**：只上传到任务指定对象键，记录七牛返回的 hash 和大小。
9. **回传**：提交完整结果，等待 MotionCare 成功确认。
10. **清理**：删除输入、输出、FFmpeg 管道文件和任务清单；立即领取下一任务。

算法处理单条视频的首版硬上限为 60 分钟，继承现有全帧流式计数设计。超过上限的任务在预检阶段以 `video_too_long` 失败，由医生填写训练结果；不得静默截断或改为抽帧。

无论成功、失败、信号中断或进程正常退出，都进入本地清理路径。服务启动时额外扫描并删除超过任务最大执行窗口的残留目录。模型文件、虚拟环境和不含患者身份的结构化日志不属于任务缓存。

## 11. 主训练者追踪与骨架可视化

主训练者追踪器是基础 PP 流水线的一部分，不属于具体动作插件。它使用人体框面积、画面中心位置和跨帧关键点/人体框连续性建立稳定身份；一旦锁定，不因另一个人短暂进入画面而切换计数对象。

追踪器输出三类结果：

- **稳定**：向插件和可视化发送唯一主训练者关键点。
- **短暂缺失或轻度歧义**：保留跟踪状态，跳过不能可靠归属的帧，并在质量摘要中降低主体覆盖率。
- **无法建立主体或长时间失锁**：任务以 `subject_unstable` 失败，防止把旁人误计为患者。

具体连续性阈值是 `subject-tracker-v1` 的版本化算法参数，不属于医生可配置项；上线前必须通过单人、旁人进入、交叉遮挡和短暂离画样本测试固定。参数变化必须升级追踪器版本并重新跑回归样本。

PP 原始多人结果不能直接用于视频输出。流水线先选出主训练者，再把单人关键点传给 PP 的骨架绘制组件。因此动作插件的计数对象和医生看到的骨架对象始终一致。

骨架视频：

- 保持原视频分辨率和时间轴；
- 仅绘制主训练者骨架；
- 不绘制其他人骨架；
- 不叠加次数、动作阶段、质量标签或患者信息；
- 不包含任何音轨。

## 12. 动作插件契约

动作插件通过处方动作的 `source_key` 注册。插件只消费标准化、单主体、带时间戳的关键点帧，不负责视频、网络、七牛云、数据库、PP 模型或骨架绘制。

概念接口：

```text
ActionAnalyzer
- action_source_key
- algorithm_version
- rule_version
- parameter_version
- consume(PoseFrame)
- finish() -> AnalysisResult
```

标准结果至少包含：

```text
total_count
standard_count
nonstandard_count
confidence_level
quality_flags
quality_summary
action_specific_details
```

肩部推举插件继续复用已经验收的 `shoulder-press-v2`：左右侧独立检测，最终次数取两侧事件数较大值，标准和不标准次数满足总数守恒。该规则不因迁移到独立服务而重新设计或调参。

## 13. 失败、重试与幂等

### 13.1 当前失败语义

以下情况任务直接失败：

- 原视频不存在、损坏、无法解码或不含视频流；
- 模型或推理依赖不可用；
- 动作插件缺失或版本不兼容；
- 无法建立稳定主训练者；
- 资源不足、磁盘不足或进程异常；
- 结果校验不通过；
- 骨架视频生成、上传或最终对象校验失败；
- 租约超时。

失败后不自动重新运行算法，也没有医生或管理员重投入口。医生可直接填写训练记录当前结果。

### 13.2 同次执行的技术重试

下载、上传、心跳和完成回传遇到超时、连接重置或明确可重试的 5xx 时，默认最多重试 3 次并使用递增退避。4xx、凭证或数据校验错误不重试。动作推理抛出失败后不重新启动推理。

完成回传使用稳定幂等键。若首次请求已经成功但响应丢失，重复请求只返回既有成功状态，不能再次覆盖医生随后修改的数据。具体规则为：任务已经 `succeeded` 且幂等键一致时返回首次完成响应；任务已经成功但幂等键不同则冲突，不重新写训练记录。

若骨架对象已上传但任务最终未成功登记，业务端根据预分配对象键创建七牛清理墓碑，删除孤儿对象。

## 14. 安全与隐私

- 内部 API 仅接受独立、可轮换的 `pp-mcare` 机器凭证，并强制 HTTPS。
- 领取响应中的七牛下载 URL 和上传凭证只对当前任务有效；上传 scope 固定为单个骨架对象键，不允许覆盖其他对象。
- 原视频和骨架视频都位于私有空间，医生播放前由 MotionCare 按行级权限签发短期下载 URL。
- `pp-mcare` 配置不包含七牛 AK/SK、数据库密码、Redis 地址或 Django 密钥。
- 日志只记录 job ID、阶段、版本、耗时、资源和稳定错误代码；不得记录患者身份、完整签名 URL、上传令牌或本地原始路径。
- 任务目录只允许专用系统用户访问，视频文件权限不宽于 `0600`。
- 医生端权限继续由 Django 接口级和行级校验保证，前端显隐不作为安全边界。

## 15. 医生端体验

训练视频详情展示自动分析状态：

- **待分析**：说明已进入队列；骨架视频不可用，结果字段不可编辑。
- **分析中**：展示分析中状态；骨架视频不可用，结果字段不可编辑。
- **分析成功**：展示原视频/骨架视频切换和当前结果字段，医生可以编辑并保存。
- **分析失败**：展示安全失败提示，允许医生填写当前结果字段。
- **暂不支持**：没有自动任务，说明该动作暂不支持自动分析，并允许医生填写结果字段。

页面不提供开始分析、重新分析或任务重试按钮。

原视频与骨架视频使用分段切换控件。切换时在目标播放器元数据加载后恢复原播放器的 `currentTime`，并尽量保持播放/暂停状态；允许编码造成的小范围时间误差。骨架视频无音轨，原视频按既有策略播放。

医生保存时校验三项计数和总数守恒，成功后显示“医生已修正”，记录修改人和时间。算法原始任务结果不随医生修改而改变。

## 16. 监控与运维

业务端和算法端使用 job ID 作为统一关联 ID。至少记录：

- worker 最后领取时间与能力版本；
- pending 任务数、最老任务等待时长；
- 当前任务阶段、最后心跳和租约到期时间；
- 下载、推理、编码、上传和回传耗时；
- 解码帧数、推理帧数和输出帧数；
- 进程峰值 RSS、系统内存、Swap 和磁盘余量；
- 成功/失败次数、稳定失败代码和本地清理结果。

空队列 15 分钟轮询意味着新任务正常情况下最迟约 15 分钟被领取。超过 20 分钟仍为 `pending` 应触发运维告警，以覆盖时钟误差和一次短暂请求失败。

算法服务器保持并发 1。正式建议规格为 2 vCPU / 4 GiB 物理内存，并保留 Swap 作为 OOM 保护。当前约 1.58 GiB 实例可作为受控试运行环境；若真实任务发生持续 Swap、OOM、系统可用内存过低或推理/编码并行峰值不可接受，则弹性升级到 4 GiB，不通过抽帧规避资源问题。

## 17. 测试与验收

### 17.1 单元测试

- `TrainingRecord` 三项计数全空/全有和总数守恒校验。
- 算法写入、医生覆盖、来源及修改人时间更新。
- 自动建任务幂等，失败任务不会因重复视频完成回调再次创建。
- claim 的动作能力匹配、最早任务选择、行锁和单任务租约。
- 心跳续约、错误令牌、过期租约和终态拒绝。
- complete 的幂等、七牛对象元数据校验和事务回滚。
- fail 与租约超时都只标记失败，不重新排队。
- 上传凭证 scope 精确绑定骨架对象键，日志脱敏。
- 视频删除或解绑时原视频和骨架对象都进入清理墓碑。

### 17.2 契约与集成测试

- 业务端与 `pp-mcare` 对 claim、heartbeat、complete、fail 负载运行同一组契约样例。
- 模拟七牛下载、上传和对象查询，验证权限过期、对象不一致和孤儿清理。
- worker 在空队列后等待 15 分钟；成功/失败后立即领取下一项。
- 下载、上传和 API 的可重试网络错误最多重试 3 次，数据错误不重试。
- 正常、失败、信号退出和重启后的本地目录清理。
- 骨架视频可解码、无音轨、时长误差符合约束。
- 多人、旁人进入、交叉遮挡和短暂离画样本只输出主训练者骨架与计数。
- 医生端五种状态、无手动分析按钮、视频切换保持时间点以及结果编辑校验。

### 17.3 真实视频回归

继续使用 SHA-256 为 `f4c7b1a4e1a7cdc192b32b73f6cb60600b02446d65f9aa471d34ee71458a78dd` 的 5 分钟视频，人工真值固定为 90：

- 8,929 个成功解码帧全部进入推理，不出现 5/10 FPS 或其他抽帧结果；
- 肩部推举总次数为 90，且结果满足总数守恒；
- 只输出主训练者骨架，无其他人员骨架和动作分析文字；
- 输出视频无音轨、可通过私有 URL 播放，并能与原视频近似同时间点切换；
- MotionCare 训练记录、任务原始结果和七牛骨架元数据一致；
- `pp-mcare` 完成后任务目录无原视频、骨架视频或中间文件残留；
- 记录耗时、峰值 RSS、Swap 和磁盘变化，作为 2 GiB 试运行是否需要升级到 4 GiB 的依据。

## 18. 发布与回退

发布顺序：

1. 部署向后兼容的数据库 migration、训练记录字段、内部任务 API 和医生端只读状态展示，但保持自动建任务关闭。
2. 在算法服务器部署 `pp-mcare`，配置机器凭证、MotionCare 地址和模型缓存，先关闭正式轮询。
3. 使用非生产训练记录完成 claim、全帧分析、骨架上传、complete 和缓存清理冒烟。
4. 开启 `pp-mcare` 正式轮询，再开启 MotionCare 自动建任务开关。
5. 使用真实视频检查 90 次回归、骨架视频、医生覆盖和资源指标。

回退时先关闭 MotionCare 自动建任务，再停止 `pp-mcare`。已经成功的训练结果和骨架视频继续可读；`pending` 任务可由运维批量标记失败，医生按失败流程填写结果。回退不删除历史任务或已上传骨架对象。

## 19. 首版验收标准

只有以下条件全部满足，首版才算完成：

1. 支持动作的视频绑定训练记录后自动创建且只创建一个任务。
2. 空队列时每 15 分钟轮询，有积压时任务连续串行执行。
3. 算法服务器不连接业务数据库、Redis/Celery，也没有七牛长期凭证。
4. 原视频每个成功解码帧都执行 PP-TinyPose，动作插件与骨架视频复用同一次推理结果。
5. 只计数和绘制主训练者；主体无法稳定锁定时安全失败。
6. MotionCare 校验骨架对象后，原子完成任务并写入训练记录当前结果。
7. 医生可切换原视频和无声骨架视频，并可覆盖同一组结果字段。
8. 失败任务不重跑，医生可直接填写结果；内部错误信息不泄露。
9. 成功或失败后算法服务器没有任务视频残留，孤儿云对象可被清理。
10. 真实回归视频全帧计数保持 90 次，并留下完整资源与运行证据。
