# 训练视频压缩与处方即时展示设计

## 1. 背景

iPhone 真机使用微信小程序 `Camera` 录制时，`resolution="medium"` 仍可能生成超过
32MB 的 30 秒 MP4 分段。生产后端会在分段上传入口按声明大小拒绝该文件，导致患者端
长期停留在 `0/N`。与此同时，患者首页已经取得完整 `current_prescription`，但点击
“查看处方”后处方页会清空数据并重复请求相同内容，在移动网络下产生约两秒的空白等待。

本设计覆盖旧设计中的录像清晰度、单段大小、总大小、最长时长和处方加载策略。既有的
30 秒连续分段、业务服务器接收、FFmpeg 合并、最终视频上传七牛、成功后清理和动作分析
主链路保持不变。

## 2. 已确认决策

1. 相机默认使用微信 `Camera` 的 `low` 录制档位。
2. 每个原始分段必须在小程序端压缩，最终尺寸不超过竖屏 `720×1280` 或横屏
   `1280×720`。
3. 压缩使用约 2Mbps 视频码率与 24fps；不传 `quality`，避免它覆盖码率、帧率和缩放参数。
4. 服务器单段上限从 32MB 调整为 50MB。
5. 服务端删除独立的“完整视频总大小”业务限制，不再按旧的 200MB 拒绝上传或完成。
6. 最长实际录像时长从 600 秒调整为 2400 秒（40 分钟）。
7. 分段仍以约 30 秒轮转，单次会话最多 80 段。
8. 压缩失败时必须保留原始分段、暂停后续上传并允许患者重试；不得直接上传未压缩文件。
9. 首页取得的处方写入进程内共享缓存；处方页优先显示缓存，再后台刷新。
10. 不升级 Taro、Django、FFmpeg、Celery、Nginx 或其它环境依赖。

## 3. 小程序录像与压缩

### 3.1 分辨率与压缩参数

`Camera` 使用：

```text
devicePosition = front
resolution = low
```

微信的 `low / medium / high` 不能保证精确输出尺寸，因此每个分段仍必须调用
`Taro.compressVideo`。先通过 `getVideoInfo` 读取原始宽高，再计算：

```text
portrait target  = 720 × 1280
landscape target = 1280 × 720
scale = min(1, targetWidth / sourceWidth, targetHeight / sourceHeight)
bitrate = 2000 kbps
fps = 24
```

原始视频小于目标尺寸时不放大，压缩仍负责控制码率。压缩结果必须重新读取
`getVideoInfo`，以压缩后的真实时长、大小和尺寸进入上传清单。

### 3.2 本地文件生命周期

分段处理顺序：

```text
Camera 返回原始临时路径
  -> saveFile 持久化原始分段
  -> 原子写入待压缩清单
  -> compressVideo
  -> 校验 720P、正数时长、正数大小、大小 <= 50MB
  -> saveFile 持久化压缩分段
  -> 原子更新为待上传分段
  -> 删除原始持久化分段
  -> 单并发上传
  -> 服务端确认后删除压缩分段
```

必须在压缩开始前持久化原始分段及其待压缩状态，以覆盖压缩期间退后台、进程退出和小程序
冷启动。旧版本已保存且没有压缩字段的待上传分段按“已压缩”兼容读取，不能破坏当前患者
手机上的恢复清单。

待压缩与已压缩分段使用可判别联合状态：

```text
pending_compression | compression_failed
  rawSavedFilePath
  durationMs
  compressionError

compressed
  savedFilePath
  durationMs
  sizeBytes
  uploadState
```

压缩失败时保留 `rawSavedFilePath`，停止该会话后续上传并显示“录像压缩失败，可重试”。
重试只重新执行该分段压缩，不重新录像；成功后按序恢复上传。患者选择重新训练时，原始和
压缩文件都按现有安全清理流程删除。

### 3.3 客户端边界

- 压缩结果超过 50MB 时不得发起网络请求，错误显示实际大小和 50MB 上限。
- 分段累计实际时长不得超过 2400 秒。
- 第 80 段完成后自动停止录像并进入收尾。
- 屏幕常亮、页面隐藏暂停、冷启动强制恢复和分段上传单并发规则保持不变。

## 4. 服务端边界

### 4.1 配置

```text
TRAINING_VIDEO_SEGMENT_MAX_SIZE_BYTES = 52428800
TRAINING_VIDEO_MAX_DURATION_SECONDS = 2400
TRAINING_VIDEO_MAX_SEGMENTS = 80
MOTION_ANALYSIS_DOWNLOAD_DEADLINE_SECONDS = 900
MOTION_ANALYSIS_STALE_TIMEOUT_SECONDS = 7200
```

删除 `TRAINING_VIDEO_MAX_SIZE_BYTES` 的配置声明、部署默认值和示例环境变量。生产环境旧值
即使暂时残留也不再被应用读取。

Nginx 当前 `client_max_body_size 80m` 高于应用层 50MB 单段上限，保持不变。现有
FFmpeg 合并超时、七牛上传超时和视频任务 stale timeout 保持不变；720P、2Mbps、
40 分钟视频预计约 600MB，现有组装与数据中心到七牛的上传窗口足够。

### 4.2 API 与任务

- 分段入口在声明大小和流式落盘两层继续执行 50MB 校验。
- 删除分段累计总大小和 `finalize` 完整视频总大小校验。
- 创建会话、分段累计和完成提交统一校验 2400 秒。
- 完成提交继续校验分段连续性、声明时长与服务端累计时长。
- 动作分析下载使用数据库中已校验的 `TrainingVideo.size_bytes` 作为本次下载精确上限，
  不再依赖全局视频总大小配置。
- 临时磁盘最低剩余空间、会话过期清理、七牛对象校验和成功后零留存规则保持不变。

“不限制总大小”表示没有独立的累计字节阈值；50MB 单段、80 段和 40 分钟仍共同构成
请求数量、单请求资源和训练时长边界。

## 5. 处方缓存与后台刷新

新增患者端进程内处方缓存模块，提供：

```text
readCurrentPrescriptionCache()
writeCurrentPrescriptionCache(value)
clearCurrentPrescriptionCache()
```

数据流：

1. 首页 `/patient-app/home/` 成功后，把响应中的 `current_prescription` 写入共享缓存。
2. 处方页初始化时读取缓存；命中后立即设置 `data` 与 `loaded=true`，不展示全页加载状态。
3. `useDidShow` 不再清空现有处方，而是后台请求 `/patient-app/current-prescription/`。
4. 后台刷新成功后同时更新页面与缓存。
5. 后台刷新失败且已有缓存时保留列表，展示非阻断提示；没有缓存时维持现有错误页。
6. 登录失效、解绑或清除患者 token 时同步清空处方缓存，避免账号之间串数据。

缓存只存在于当前小程序进程，不写长期本地存储。冷启动仍由首页或处方接口取得最新数据；
因此不会跨启动展示旧处方，也不引入缓存版本迁移。

## 6. 错误处理

- 录制失败：保持现有摄像头权限与录制失败提示。
- 原始文件持久化失败：结束录像，进入现有恢复流程。
- 压缩失败：保留原始文件和错误状态，允许重试，不上传原始文件。
- 压缩结果无效或超过 50MB：按压缩失败处理，并显示可理解的体积信息。
- 上传失败：保留压缩文件，沿用现有上传重试。
- 处方后台刷新失败：有缓存时保留内容，无缓存时显示加载失败。
- 服务端仍不向患者暴露路径、密钥、FFmpeg 命令或内部异常。

## 7. 测试与验收

### 小程序

- 相机使用 `low` 档位。
- 横竖屏缩放比例都不会超过 720P 目标，且不放大小视频。
- 压缩使用 2Mbps、24fps，压缩成功后上传压缩文件而非原始文件。
- 压缩前原始文件已持久化；压缩成功删除原始文件，上传成功删除压缩文件。
- 压缩失败、冷启动恢复和手动重试均保留同一分段序号。
- 压缩结果 50MB 边界允许，超过边界不发起上传。
- 2400 秒与第 80 段正常收尾，超过边界被拒绝。
- 旧版本待上传清单可继续读取和上传。
- 首页缓存处方后，处方页首帧直接显示动作列表。
- 后台刷新成功替换缓存；刷新失败保留已展示数据；退出登录清除缓存。

### 后端

- 50MB 分段允许，超过 50MB 在声明校验和流式落盘两层均拒绝。
- 累计大小超过旧 200MB 后仍允许上传与 `finalize`。
- 2400 秒允许，超过 2400 秒拒绝。
- 最多 80 段，超过 80 段拒绝。
- 动作分析按当前视频实际大小下载，不依赖已删除的总大小配置。
- 配置默认值、部署环境映射和 stale timeout 关系均通过启动测试。

### 发布

1. 完整运行后端测试。
2. 完整运行小程序测试与生产构建。
3. 检查差异与生产构建中的 API 域名。
4. 使用中文提交信息提交并推送 `main`。
5. 沿用现有镜像和部署脚本发布 API、Celery 与微信静态站，不升级依赖。
6. 更新生产环境中的单段、时长和动作分析超时配置并核对容器实际值。
7. 上传新的微信小程序开发版本并生成真机二维码。
8. 真机验证首段上传达到 `1/1`，并验证处方列表即时出现。

## 8. 非目标

- 不改变医生端视频播放和动作分析交互。
- 不增加服务端转码清晰度档位。
- 不把原始分段上传服务器或七牛。
- 不改变 Nginx 请求体上限。
- 不升级依赖、操作系统、数据库、Redis、FFmpeg 或容器基础镜像。
