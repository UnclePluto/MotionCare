# 微信小程序游戏演示模式设计

## 目标

为微信小程序审核和功能体验提供固定入口：在绑定页输入 `8888` 后进入现有首页，并可体验全部六个游戏。演示过程不创建真实账号、不访问用户业务接口、不上传训练结果，也不读写真实用户留下的训练缓存。

该入口永久保留在开发版和正式构建中。当前工作完成后只上传微信开发版，不提交微信审核或正式发布。

## 已确认体验

### 进入方式与身份

- 未绑定状态下，在现有绑定页输入 `8888` 并点击绑定按钮。
- 前端直接开启演示模式，不调用 `Taro.login`，不请求 `/patient-app/bind/`，不写入真实 token。
- 随后进入现有首页，展示：
  - 用户名称：`用户01`
  - 项目名称：`功能展示`
  - 顶部提示：`演示模式，仅供功能体验，数据不会保存。`
- 如果设备已有真实登录 token，继续沿用现有逻辑直接进入真实首页；演示入口不覆盖已登录身份。

### 演示首页

- 保留“查看运动计划”，进入包含全部六个游戏的运动计划页。
- 保留“开始训练”，直接进入运动计划中的第一个游戏。
- 隐藏训练历史等依赖服务端真实记录的入口。
- 不增加“退出演示”按钮；微信关闭或回收小程序进程后自动退出演示模式。

### 演示运动计划

运动计划固定包含以下六个游戏，不包含摄像训练或其他动作：

1. 颜色顺序记忆
2. 图案顺序记忆
3. 反应抑制
4. 分类切换
5. 声音辨别
6. 拼图

每个游戏的建议时长为 1 分钟，默认难度为“简单”。列表继续复用现有运动计划卡片和游戏分包加载流程，但不显示依赖真实服务端记录的历史入口、最近记录或补传提示。

### 游戏与结果

- 六个游戏继续复用现有介绍、设置、训练、暂停、计时、正常完成和提前结束流程。
- 正常完成或提前结束后，继续计算并展示得分、正确率、错误次数、实际难度、训练时长、结束方式和完成题数。
- 结果仅保存在当前游戏页面的内存状态中，不调用训练记录接口，不写待补传缓存，不启动后台补传。
- 结果页上传状态改为“本次演示不保存”，不显示上传失败或待补传文案。
- 演示结果页点击“返回运动计划”时固定进入包含六个游戏的运动计划页；即使用户从首页“开始训练”进入，也不直接返回首页。

## 技术设计

### 进程内演示会话

新增小程序演示会话模块，使用模块级内存状态保存是否处于演示模式：

- `startDemoSession()`：绑定页识别 `8888` 后开启。
- `isDemoSession()`：页面和应用生命周期读取当前模式。
- 不调用 `Taro.setStorageSync`，不写 token，不新增 cookie 或服务端会话。
- 小程序切到后台再回前台时，只要进程仍在，演示模式继续存在。
- 微信关闭或回收进程后模块重新初始化，演示模式自动失效。

测试通过重载模块模拟进程重启，不在生产代码中提供持久化或面向用户的重置接口。

### 固定演示数据

新增独立的演示数据模块，以工厂函数返回新的 `HomeData` 和 `CurrentPrescription` 对象，避免页面修改共享常量。数据满足现有类型契约：

- 身份固定为 `用户01` / `功能展示`。
- 使用仅前端可见的稳定正整数 ID。
- 运动计划包含六个 `internal_type: 'game'` 动作，并使用现有游戏目录支持的六个 `source_key`。
- 每个动作 `duration_minutes: 1`、`difficulty: '简单'`。
- 周目标可展示，但完成次数、最近记录固定为空或零，不用演示结果回写。

演示数据不模拟历史数据，也不与真实 API 响应或缓存合并。

### 显式数据源选择

新增小程序用户数据加载层，由页面显式调用：

- 演示模式：返回固定演示首页和运动计划数据。
- 真实模式：继续请求 `/patient-app/home/` 与 `/patient-app/current-prescription/`。

不在通用 `request` 函数里拦截 URL，也不伪造认证 token。这样演示边界可被测试直接识别，真实接口错误、鉴权和请求行为保持不变。

首页、运动计划页和游戏页统一使用该数据加载层，避免任何一个入口遗漏后误发真实请求。

### 真实缓存和补传隔离

演示模式必须绕过以下真实数据副作用：

- 不读写当前运动计划缓存。
- 不读取、保存、覆盖或删除 `motioncare.pendingGameUpload`。
- 不调用游戏训练结果上传接口，不启动或恢复游戏补传循环。
- 不检查或跳转肩部推举待上传录像。
- 不显示真实待补传横幅。

绑定页识别 `8888` 后立即停止当前进程中的游戏补传定时器，但不清除任何真实缓存。应用回到前台时，若处于演示模式则跳过录像恢复和游戏补传；若既不是演示模式也没有真实 token，同样不启动需要认证的恢复流程。真实登录用户继续执行原有恢复与补传逻辑。

### 页面行为分支

- 绑定页只对精确的四位代码 `8888` 走演示分支，其他四位代码保持原绑定流程和错误处理。
- 首页在演示模式展示演示提示，只显示“查看运动计划”和“开始训练”。
- 运动计划页在演示模式不注册补传监听、不触发待上传处理、不显示历史按钮。
- 游戏页在演示模式从固定运动计划寻找动作；结束时只设置页面内结果状态，不执行 `uploadResult`。
- 真实模式的首页操作、历史入口、缓存、上传、重试和录像恢复保持现状。

## 安全与数据边界

- `8888` 只开启前端展示状态，不可换取真实 token，也不能获得任何后端权限。
- 演示模式不访问首页、运动计划、训练记录或绑定业务接口。
- 直接调用后端仍必须通过现有真实鉴权；演示状态不参与请求头生成。
- 演示身份、运动计划和结果均不写入服务端。
- 不使用、不保存 AppSecret；发布继续通过已配置的微信开发者工具上传能力完成。

## 错误与边界处理

- 游戏分包加载失败继续显示现有重试提示；这不属于业务数据请求。
- 固定演示数据若缺少对应游戏目录项，按现有无效动作错误处理，并由测试防止该情况进入发布版本。
- 模块重载后若用户停留在需要演示数据的页面，视为进程已重启，应按现有未登录流程回到绑定页，而不是恢复演示状态。
- 演示模式不会消费真实待上传记录；重新以真实身份进入后，现有补传机制仍可继续处理该记录。

## 测试与验收

### 自动化测试

- 输入 `8888`：不调用 `Taro.login`、绑定接口或 token 存储，并进入首页。
- 输入普通四位绑定码：继续调用真实登录、绑定和 token 存储流程。
- 演示首页和运动计划：不发业务网络请求，不读写运动计划或待补传缓存。
- 演示首页展示 `用户01`、`功能展示`、提示横幅及两个允许入口，不展示训练历史。
- 演示运动计划完整展示六个游戏，且每个游戏均可进入现有训练页。
- 六个游戏正常完成和提前结束后均展示本地结果，不调用训练记录接口、不保存待补传记录。
- 演示结果页返回完整运动计划。
- 应用前后台切换期间演示状态保留，并跳过真实录像恢复和游戏补传。
- 重载演示会话模块后状态恢复为关闭，验证未使用本地持久化。
- 真实身份的首页、运动计划、训练上传、失败补传和后台恢复回归测试保持通过。
- 小程序中性术语静态校验保持通过。

### 构建与发布验收

- 运行小程序全量测试。
- 运行开发微信构建和生产微信构建。
- 生产构建继续注入 `https://mcare-wx.whestsun.com/api`，真实流程不得受演示数据影响。
- 复审通过后提交并推送 `main`。
- 上传微信开发版版本 `2026.08.12.1`，描述固定为 `性能优化`。
- 不提交微信审核、不发布正式版；微信公众平台中的开发版本可见性由平台侧人工确认。
