# PP-TinyPose 全帧流式肩部推举计数 v2 设计

## 1. 背景

独立算法服务器已经使用 `PP-TinyPose_128x96` 完成同一段 5 分钟视频的 5 FPS、10 FPS 和全帧冒烟测试。视频实际时长为 300 秒、共解码 8,929 帧，人工计数真值为 90 次。

现有 `shoulder-press-v1` 规则得到：

- 5 FPS：44 次；
- 10 FPS：44 次；
- 全帧：60 次。

进一步诊断显示，PP-TinyPose 并未漏掉主要动作周期。基于左右手腕归一化抬升曲线的独立峰值检测，在多组最小间隔和峰值突出度组合下均稳定得到 90 个峰值。漏计主要来自业务规则层：固定选择左侧、`down` 状态门槛过严、连续帧数和持续时间使用 `OR` 导致采样率改变语义，以及先平均左右坐标再计算角度。

本设计用人工真值做回归验收，但禁止写入“强制输出 90”或只匹配该视频的特殊分支。

## 2. 已确认决策

1. 正式分析默认使用视频原始全部帧，不抽帧。
2. 处理方式改为流式，不能在内存中累积整段关键点列表。
3. 当前 2 vCPU 保持不变，物理内存升级到 4 GiB，并保留 4 GiB Swap；使用 CPU 推理，分析并发固定为 1。
4. 单条视频最长按 60 分钟设计。
5. PP-TinyPose 只负责人体关键点检测；动作计数和质量判断继续由 MotionCare 规则层负责。
6. 左右手臂独立测量并在事件层融合，禁止平均左右关键点坐标。
7. 计数依据完整运动周期；肘部角度只影响动作质量，不再作为计数硬门槛。
8. 保持现有 HTTP API 和 `MotionAnalysisJob` 核心计数字段兼容。
9. 新规则版本为 `shoulder-press-v2`；模型版本继续单独记录。
10. 本期仍只支持肩部推举，不泛化为任意动作识别系统。

## 3. 目标与非目标

### 3.1 目标

- 在全帧模式下对人工标注视频稳定计出 90 次。
- 让计数结果由时间和运动形态决定，不随视频 FPS 改变。
- 让内存占用近似固定，不随视频时长或总帧数线性增长。
- 分离“是否发生一次动作”和“动作是否标准”。
- 输出左右侧依据、关键点覆盖率和置信度，便于解释和后续标注。
- 保持医生端现有任务创建、轮询和结果展示不失效。

### 3.2 非目标

- 不训练新的时序神经网络。
- 不支持肩部推举之外的动作类型。
- 不提供实时摄像头纠错。
- 不把一个样例的通过解释为临床有效性证明。
- 不改变视频存储供应商、上传流程或数据库网络拓扑。
- 不增加多任务并发；扩容和横向调度留到后续阶段。

## 4. 方案选择

采用“全帧流式关键点 + 单侧运动峰值 + 双侧事件融合”。

未采用的方案：

- 修补 v1 状态机：改动较小，但诊断中右侧最好仅得到 86 次，仍依赖脆弱的上下姿态门槛。
- 训练时序模型：长期可能更强，但当前没有足够的动作起止点标注数据，投入与首版目标不匹配。

## 5. 总体架构

```text
临时视频文件
  -> 顺序解码全部视频帧
  -> PP-TinyPose 单帧关键点
  -> 左右侧归一化特征
  -> 每侧短时平滑与峰谷状态机
  -> 左右动作事件融合
  -> 次数、质量、置信度和紧凑动作明细
  -> MotionAnalysisJob
```

处理过程中只保留：

- 平滑所需的短时帧窗口；
- 左右两侧当前候选周期的少量标量状态；
- 已确认动作的紧凑摘要。

不保留整段原始图像或整段逐帧关键点。60 分钟相对 5 分钟只增加推理时间和动作摘要数量，不应导致关键点内存线性增长。

## 6. 组件边界

### 6.1 全帧关键点迭代器

`pose_inference` 提供惰性关键点迭代器，负责：

- 按解码顺序读取视频；
- 每个成功解码帧执行一次 PP-TinyPose；
- 产出单调递增的 `timestamp_ms` 和标准化关键点；
- 在迭代完成、异常或调用方提前退出时释放 `VideoCapture`；
- 视频无可分析帧时抛出明确的推理异常。

配置 `MOTION_ANALYSIS_SAMPLE_FPS` 支持：

- `all`：全部成功解码帧，作为默认值；
- 正浮点数：仅用于诊断、回归和紧急降级。

内部用 `sample_fps=None` 表示全帧，禁止用 `0` 作为隐式魔法值。既有正数环境变量继续兼容。

### 6.2 单侧特征提取器

左右侧分别使用肩、肘、腕、髋关键点。单侧有效帧要求四个关键点均可解析，最低置信度沿用 `0.4`。

主要计数特征为：

```text
wrist_lift = (shoulder_y - wrist_y) / torso_length
torso_length = distance(shoulder, hip)
```

躯干长度必须大于零。肘角、关键点最低置信度和有效性同步计算，但不参与左右坐标平均。

### 6.3 单侧流式事件检测器

每侧维护按时间裁剪的平滑窗口和一个候选周期状态机。初始参数为：

| 参数 | 初始值 | 含义 |
| --- | ---: | --- |
| 平滑窗口 | 200 ms | 对 `wrist_lift` 做滚动中位数，抑制单帧抖动 |
| 最小峰值突出度 | 0.15 torso | 候选峰值相对前序谷值的最低有效幅度 |
| 上升迟滞 | 0.08 torso | 从谷值进入明确上升所需变化 |
| 回落迟滞 | 0.08 torso | 从候选峰值确认明显回落所需变化 |
| 同侧最小动作间隔 | 800 ms | 防止同一动作产生重复峰值 |
| 关键点短缺口 | 300 ms | 缺失不超过该时长时保留候选状态 |
| 最短动作时长 | 800 ms | 质量判断下限 |
| 最长动作时长 | 8,000 ms | 质量判断上限 |

一次单侧动作事件必须经历：

```text
局部谷值 -> 明显上升 -> 达到有效峰值 -> 明显回落
```

只有峰值相对谷值达到最低突出度且已经明显回落时才确认事件。视频开头已处于高位、视频结尾尚未回落的半次动作不计数。

关键点缺失不超过 300 ms 时保留状态但不伪造测量值；超过 300 ms 时放弃尚未完成的候选周期并重新同步。不得跨长缺口拼接一次动作。

### 6.4 双侧事件融合器

左右事件先独立生成，再按峰值时间融合：

- 左右峰值相差不超过 400 ms，合并为一次双侧动作；
- 只有一侧形成可靠事件时仍计为一次；
- 若另一侧同期关键点可见却没有匹配事件，标记 `bilateral_mismatch`；
- 若另一侧同期不可见，标记结果依据为单侧并降低置信度，不直接判动作不标准；
- 超出 400 ms 的两个可靠单侧事件保留为两个动作事件。

双侧事件的 `start_ms` 取参与事件的最早开始时间，`peak_ms` 取左右峰值时间的整数中点，`end_ms` 取最晚结束时间。单侧事件直接使用该侧时间。`source_sides` 明确记录本次计数依据。

融合发生在事件层，不允许重新引入左右坐标平均。

## 7. 计数与质量判定

### 7.1 计数

形成完整的融合运动周期即计入 `total_count`。计数不要求肘角达到标准阈值。

### 7.2 标准性

每次动作独立生成质量标记：

- `range_too_small`：峰值抬升未达到 `0.55 torso`，或峰值突出度低于 `0.20 torso`；
- `elbow_not_extended`：峰值附近肘角小于 150 度；
- `tempo_abnormal`：动作时长短于 800 ms 或长于 8,000 ms；
- `low_confidence`：动作关键阶段的有效关键点覆盖率低于 80%，或峰值关键点最低置信度小于 0.4；
- `bilateral_mismatch`：两侧均清晰可见，但只有一侧形成匹配事件。

双侧事件对每个可靠参与侧分别检查幅度和肘角，任一可靠侧未达标即添加对应质量标记；不可见的一侧不据此添加动作质量标记。单侧事件只检查产生该事件的一侧。

没有质量标记的动作计入 `standard_count`；有任一质量标记的动作计入 `nonstandard_count`。始终满足：

```text
total_count = standard_count + nonstandard_count
```

这些阈值属于 `shoulder-press-v2`，后续只有在新增人工标注数据并做回归对照后才能调整版本。

## 8. 结果契约

数据库现有字段保持不变：

- `algorithm_name = pp-tiny-pose`；
- `algorithm_version` 记录实际 PP-TinyPose 模型版本；
- `rule_version = shoulder-press-v2`；
- `total_count`、`standard_count`、`nonstandard_count` 继续用于列表和前端摘要。

`result_payload` 保留现有字段并扩充为：

```json
{
  "total_count": 90,
  "standard_count": 82,
  "nonstandard_count": 8,
  "rule_version": "shoulder-press-v2",
  "processed_frames": 8929,
  "source_fps": 29.763,
  "analysis_elapsed_ms": 445457,
  "left_event_count": 90,
  "right_event_count": 90,
  "bilateral_event_count": 90,
  "bilateral_agreement_ratio": 1.0,
  "keypoint_coverage_ratio": 0.995,
  "confidence_level": "high",
  "rep_details": [
    {
      "index": 1,
      "start_ms": 1200,
      "peak_ms": 2750,
      "end_ms": 3900,
      "duration_ms": 2700,
      "source_sides": ["left", "right"],
      "is_standard": true,
      "flags": []
    }
  ],
  "quality_flags": ["camera_angle_unverified"]
}
```

指标定义如下：

- 单侧覆盖率：该侧四个必需关键点均有效的帧数除以已处理帧数；
- 整体关键点覆盖率：至少一侧有效的帧数除以已处理帧数；
- 双侧一致率：成功匹配为双侧事件的数量除以 `max(left_event_count, right_event_count, 1)`，结果限制在 0 到 1；
- `high`：整体覆盖率不低于 90%，且双侧一致率不低于 80%；
- `medium`：整体覆盖率不低于 70%，且双侧一致率不低于 50%，但未达到 `high`；
- `low`：其余仍能产生有效计数的情况。

置信度用于提示结果可靠程度，不修改 `total_count`。如果动作本身明确为单侧训练，未来应由该动作自己的规则器定义置信度；本期肩部推举按双侧动作处理。

## 9. 失败与资源清理

下列情况任务标记为 `failed`：

- 视频无法打开或没有可解码帧；
- PP-TinyPose 依赖或模型加载失败；
- 全程没有可用的人体关键点；
- 结果计数不满足持久化约束；
- 未捕获的推理或规则异常。

部分遮挡、画面抖动、左右结果差异和低覆盖率不直接失败。任务成功保存可用计数，并通过 `confidence_level`、动作标记和 `quality_flags` 告知调用方。

无论成功、失败或生成器提前关闭，都必须释放视频句柄并删除任务临时视频。异常信息继续使用现有脱敏失败原因，不返回本地路径、凭证或 traceback。

## 10. 任务执行与部署约束

- 动作分析 Worker 固定并发 1。
- 正式机器保持当前 2 vCPU，物理内存升级到 4 GiB，并保留现有 4 GiB Swap 作为 OOM 保护。
- 正常任务不应使用 Swap；发生持续 Swap 表示资源或实现异常。
- 现有 `MOTION_ANALYSIS_STALE_TIMEOUT_SECONDS=7200` 保留，可覆盖当前实测推算的 60 分钟视频约 74 分钟分析时间。
- 当前全帧实测约为视频时长的 1.48 倍；上线硬目标为不超过 2 倍。
- 本期不承诺实时处理，也不允许同一 Worker 并行分析多个视频。

当前 5 分钟全帧实测峰值 RSS 约 682 MiB，系统最低仍有约 751 MiB 可用内存，Swap 使用为零。升级到 4 GiB 为单任务运行提供足够余量，但内存扩容不能替代流式改造。

## 11. 测试设计

### 11.1 单元测试

- 完整周期只计一次；开头和结尾半次动作不计数。
- 峰值突出度、上升/回落迟滞和 800 ms 去重边界。
- 5、10、30 FPS 与非恒定时间戳下，同一合成动作序列得到相同次数。
- 300 ms 内短暂缺失保留候选状态，超过 300 ms 放弃未完成周期。
- 左右同步事件正确合并，单侧遮挡不漏计，清晰可见但不匹配产生质量标记。
- 幅度、肘角、节奏和置信度只影响标准性，不删除已形成的动作。
- 结果始终满足总数等式，动作时间按顺序且不重叠。

### 11.2 推理与任务集成测试

- 全帧配置逐个消费解码帧，不跳帧。
- 正数 FPS 配置继续支持诊断降采样。
- 关键点迭代器为惰性，不在调用前读取完整视频。
- 正常完成、消费异常和提前关闭时均释放视频句柄。
- Celery 任务保存 `shoulder-press-v2` 和扩展结果字段。
- 现有分析创建、查询、失败重试和最近结果接口保持兼容。
- 60 分钟合成流验证检测器内存不随帧数线性增长。

### 11.3 真实视频验收

使用 SHA-256 为 `f4c7b1a4e1a7cdc192b32b73f6cb60600b02446d65f9aa471d34ee71458a78dd` 的 5 分钟视频：

- 全帧计数必须等于人工真值 90；
- 相同环境重复运行结果必须一致；
- 5 FPS、10 FPS 回归结果与全帧相差不超过 1 次；
- 全帧总耗时不超过视频时长的 2 倍；
- 应用进程峰值 RSS 低于 1.5 GiB；
- 正常运行 Swap 使用量保持为零；
- 服务器分析结束后删除输入视频和中间文件。

完整后端测试、Ruff、前端测试、Lint 和构建继续按项目完成门槛执行。

## 12. 上线与回退

1. 先在本地通过规则单元测试和任务集成测试。
2. 将候选版本部署到独立算法服务器，不改变公网端口和 SSH 安全设置。
3. 使用同一人工标注视频执行全帧验收并保存脱敏报告。
4. 验收通过后将 Worker 默认配置切换为 `all` 和 `shoulder-press-v2`。
5. 保留当前 `77b0166` 对应的服务器部署归档；若 v2 违反计数、资源或接口验收，回退应用代码和默认规则版本。

回退只恢复算法应用，不回退数据库记录。历史 `MotionAnalysisJob` 通过各自的 `rule_version` 保持可审计。

## 13. 后续演进

只有在积累多段人工标注视频后，才进入以下工作：

- 按拍摄角度、患者体型和动作速度建立验证集；
- 校准质量阈值及置信度分级；
- 评估更多动作的独立规则器或时序模型；
- 根据排队时长决定纵向升级 CPU 或增加单并发 Worker 实例。

上述演进不属于本次 v2 实施范围。
