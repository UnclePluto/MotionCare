# PP-TinyPose 全帧流式肩部推举计数 v2 设计

## 1. 背景

独立算法服务器已经使用 `PP-TinyPose_128x96` 完成同一段 5 分钟视频的 5 FPS、10 FPS 和全帧冒烟测试。视频实际时长为 300 秒、共解码 8,929 帧，人工计数真值为 90 次。

现有 `shoulder-press-v1` 规则得到：

- 5 FPS：44 次；
- 10 FPS：44 次；
- 全帧：60 次。

进一步诊断显示，PP-TinyPose 并未漏掉主要动作周期。基于左右手腕归一化抬升曲线的独立峰值检测，在多组最小间隔和峰值突出度组合下均稳定得到 90 个峰值。漏计主要来自业务规则层：固定选择左侧、`down` 状态门槛过严、连续帧数和持续时间使用 `OR` 导致采样率改变语义，以及先平均左右坐标再计算角度。

本设计用人工真值做回归验收，但禁止写入“强制输出 90”或只匹配该视频的特殊分支。

首次部署 commit `7868e6c` 时，5 FPS / 10 FPS / 全帧分别得到 113 / 108 / 118 次并回退。脱敏报告显示三档左右侧事件数均为 90 / 90，但旧的“400 ms 内匹配后取左右事件并集”只匹配 67 / 72 / 62 对，把同一个双侧动作拆成两个计数。用户据此批准最终计数改为左右独立事件数的较大值；双侧匹配只承担质量、一致性和置信度语义，不再增加总数。

## 2. 已确认决策

1. 正式分析默认使用视频原始全部帧，不抽帧。
2. 处理方式改为流式，不能在内存中累积整段关键点列表。
3. 当前 2 vCPU 保持不变，生产部署目标为 4 GiB 物理内存并保留 4 GiB Swap；使用 CPU 推理，分析并发固定为 1。
4. 单条视频最长按 60 分钟设计。
5. PP-TinyPose 只负责人体关键点检测；动作计数和质量判断继续由 MotionCare 规则层负责。
6. 左右手臂独立测量，最终次数取左右事件数的较大值；动作明细以确定性锚点侧生成，禁止平均左右关键点坐标。
7. 计数依据完整运动周期；肘部角度只影响动作质量，不再作为计数硬门槛。
8. 保持现有 HTTP API 和 `MotionAnalysisJob` 核心计数字段兼容。
9. 新规则版本为 `shoulder-press-v2`；模型版本继续单独记录。
10. 本期仍只支持肩部推举，不泛化为任意动作识别系统。
11. 双侧事件匹配只影响动作质量、双侧一致率和整体置信度，不改变 `total_count`。
12. 当前 `shoulder-press-v2` 生产与验收入口只允许全帧；不再暴露 5/10 FPS 或任意正数采样配置。

## 3. 目标与非目标

### 3.1 目标

- 在全帧模式下对人工标注视频稳定计出 90 次。
- 让计数结果由时间和运动形态决定，不随视频 FPS 改变。
- 让内存占用近似固定，不随视频时长或总帧数线性增长。
- 分离“是否发生一次动作”和“动作是否标准”。
- 输出左右侧依据、关键点覆盖率和置信度，便于解释和后续标注。
- 保持医生端现有任务创建、轮询和结果展示不失效。

### 3.2 非目标

- 不训练新的时序神经网络。
- 不支持肩部推举之外的动作类型。
- 不提供实时摄像头纠错。
- 不把一个样例的通过解释为临床有效性证明。
- 不改变视频存储供应商、上传流程或数据库网络拓扑。
- 不增加多任务并发；扩容和横向调度留到后续阶段。

## 4. 方案选择

采用“全帧流式关键点 + 单侧运动峰值 + 确定性锚点计数 + 双侧质量匹配”。

未采用的方案：

- 修补 v1 状态机：改动较小，但诊断中右侧最好仅得到 86 次，仍依赖脆弱的上下姿态门槛。
- 训练时序模型：长期可能更强，但当前没有足够的动作起止点标注数据，投入与首版目标不匹配。

## 5. 总体架构

```text
临时视频文件
  -> 顺序解码全部视频帧
  -> PP-TinyPose 单帧关键点
  -> 左右侧归一化特征
  -> 每侧短时平滑与峰谷状态机
  -> 选择锚点侧并对另一侧做单调质量匹配
  -> 次数、质量、置信度和紧凑动作明细
  -> MotionAnalysisJob
```

处理过程中只保留：

- 平滑所需的短时帧窗口；
- 左右两侧当前候选周期的少量标量状态；
- 已确认动作的紧凑摘要。

不保留整段原始图像或整段逐帧关键点。60 分钟相对 5 分钟只增加推理时间和动作摘要数量，不应导致关键点内存线性增长。

## 6. 组件边界

### 6.1 全帧关键点迭代器

`pose_inference` 提供惰性关键点迭代器，负责：

- 按解码顺序读取视频；
- 每个成功解码帧执行一次 PP-TinyPose；
- 产出单调递增的 `timestamp_ms` 和标准化关键点；
- 在迭代完成、异常或调用方提前退出时释放 `VideoCapture`；
- 视频无可分析帧时抛出明确的推理异常。

当前生产配置不再定义 `MOTION_ANALYSIS_SAMPLE_FPS`。内部继续用 `sample_fps=None` 表示全帧，禁止用 `0` 作为隐式魔法值。

任务执行按已固化的 `rule_version` 精确解析分析器：历史 `shoulder-press-v1` 固定使用 5 FPS，保留旧任务执行语义；`shoulder-press-v2` 固定使用 `sample_fps=None`，即使运行环境残留旧的正数设置也不能降采样。底层正数 `sample_fps` 仅为 v1 历史兼容保留，不属于当前 v2 的公开生产、benchmark 或 smoke 入口。

历史 v1 的固定 FPS 兼容路径必须先验证解码器 `CAP_PROP_POS_MSEC` 为有限值；NaN 或正负无穷时间戳回退为 `frame_index * 1000 / source_fps`，再执行严格递增校正。遇到异常巨大的有限时间戳时，下一采样游标按跨过的完整间隔 O(1) 跳算，禁止逐间隔循环推进而占死单 Worker；无法得到有限下一游标时安全停止继续采样。

### 6.2 单侧特征提取器

左右侧分别使用肩、肘、腕、髋关键点。四个关键点坐标均可解析且躯干长度大于零时，该侧属于“可测量”；四点最低置信度不低于 `0.4` 时，该侧进一步属于“可靠”。可测量值参与运动周期检测，可靠比例用于动作质量和整体置信度，避免低分帧直接切断完整周期。

主要计数特征为：

```text
wrist_lift = (shoulder_y - wrist_y) / torso_length
torso_length = distance(shoulder, hip)
```

躯干长度必须大于零。肘角、关键点最低置信度和有效性同步计算，但不参与左右坐标平均。

### 6.3 单侧流式事件检测器

每侧维护按时间裁剪的平滑窗口和一个候选周期状态机。初始参数为：

| 参数 | 初始值 | 含义 |
| --- | ---: | --- |
| 平滑窗口 | 200 ms | 对 `wrist_lift` 做滚动中位数，抑制单帧抖动 |
| 最小峰值突出度 | 0.15 torso | 候选峰值相对前序谷值的最低有效幅度 |
| 上升迟滞 | 0.08 torso | 从谷值进入明确上升所需变化 |
| 回落迟滞 | 0.08 torso | 从候选峰值确认明显回落所需变化 |
| 同侧最小动作间隔 | 800 ms | 防止同一动作产生重复峰值 |
| 关键点短缺口 | 300 ms | 缺失不超过该时长时保留候选状态 |
| 最短动作时长 | 800 ms | 质量判断下限 |
| 最长动作时长 | 8,000 ms | 质量判断上限 |

一次单侧动作事件必须经历：

```text
局部谷值 -> 明显上升 -> 达到有效峰值 -> 明显回落
```

只有峰值相对谷值达到最低突出度且已经明显回落时才确认事件。视频开头已处于高位、视频结尾尚未回落的半次动作不计数。

关键点坐标不可测量的缺口不超过 300 ms 时保留状态但不伪造测量值；超过 300 ms 时放弃尚未完成的候选周期并重新同步。不得跨长缺口拼接一次动作。低于 0.4 但坐标仍可测量的帧不触发缺口重置，只降低可靠覆盖率。

### 6.4 锚点侧与双侧质量匹配器

左右事件先独立生成。最终明细选择一个确定性锚点侧：

- 事件数更多的一侧为锚点；
- 事件数相同时，事件平均 `coverage_ratio` 更高的一侧为锚点；
- 事件数和平均覆盖率仍相同时固定选择左侧。

每个锚点事件固定产生一条 `rep_details`，因此 `total_count = max(left_event_count, right_event_count)`。另一侧事件只按时间顺序单调、一对一匹配；已匹配事件不能复用，未匹配的非锚点事件不增加总数或明细。

双侧质量匹配按以下顺序判定：

- 左右峰值相差不超过 400 ms 时直接匹配；
- 峰值差为 401–800 ms 时，仅当两个动作区间时长均为正，且重叠长度至少占较短区间的 50% 时匹配；
- 800 ms 和 50% 边界均包含在匹配范围内；扩展匹配明确拒绝零时长或负时长事件。

匹配只影响 `bilateral_event_count`、`bilateral_agreement_ratio`、质量标记和标准/不标准分类，不改变最终次数。若另一侧同期关键点可靠但没有匹配事件，锚点明细标记 `bilateral_mismatch`；若另一侧同期不可见，则保留单侧依据并降低置信度，不直接判定动作不标准。

无论是否匹配，明细的 `start_ms`、`peak_ms`、`end_ms` 和 `duration_ms` 都严格使用锚点事件的时间；`tempo_abnormal` 也只按锚点时长判定。匹配侧不得用更早开始、更晚结束或平均峰值扩张锚点时间线，以免相邻锚点明细发生时间交叠。`source_sides` 仍明确记录锚点侧和成功匹配侧的质量判断依据。匹配发生在紧凑事件层，不允许重新引入左右坐标平均。

## 7. 计数与质量判定

### 7.1 计数

左右侧各自形成完整运动周期后，`total_count` 固定取 `max(left_event_count, right_event_count)`；每个锚点事件只产生一条计数明细，未匹配的非锚点事件不额外计数。计数不要求肘角达到标准阈值，也不依赖双侧质量匹配是否成功。

### 7.2 标准性

每次动作独立生成质量标记：

- `range_too_small`：可靠覆盖率不低于 80% 的参与侧中，峰值抬升未达到 `0.55 torso`，或峰值突出度低于 `0.20 torso`；
- `elbow_not_extended`：可靠覆盖率不低于 80% 的参与侧中，峰值附近肘角小于 150 度；
- `tempo_abnormal`：锚点动作时长短于 800 ms 或长于 8,000 ms；
- `low_confidence`：动作周期内置信度不低于 0.4 的可靠测量覆盖率低于 80%；
- `bilateral_mismatch`：锚点动作期间另一侧可靠可见，但没有按直接峰值或扩展区间规则形成匹配事件。

双侧事件只对 `coverage_ratio >= 0.8` 的可靠参与侧检查幅度和肘角，任一可靠侧未达标即添加对应质量标记；低于 80% 的参与侧不贡献 `range_too_small` 或 `elbow_not_extended`，只贡献 `low_confidence`。单侧事件同样只在产生该事件的一侧达到 80% 可靠覆盖率时检查幅度和肘角。

没有质量标记的动作计入 `standard_count`；有任一质量标记的动作计入 `nonstandard_count`。始终满足：

```text
total_count = standard_count + nonstandard_count
```

这些阈值属于 `shoulder-press-v2`，后续只有在新增人工标注数据并做回归对照后才能调整版本。

## 8. 结果契约

数据库现有字段保持不变：

- `algorithm_name = pp-tiny-pose`；
- `algorithm_version` 记录实际 PP-TinyPose 模型版本；
- `rule_version = shoulder-press-v2`；
- `total_count`、`standard_count`、`nonstandard_count` 继续用于列表和前端摘要。

`result_payload` 保留现有字段并扩充为：

```json
{
  "total_count": 90,
  "standard_count": 82,
  "nonstandard_count": 8,
  "rule_version": "shoulder-press-v2",
  "processed_frames": 8929,
  "source_fps": 29.763,
  "analysis_elapsed_ms": 445457,
  "left_event_count": 90,
  "right_event_count": 90,
  "bilateral_event_count": 90,
  "bilateral_agreement_ratio": 1.0,
  "keypoint_coverage_ratio": 0.995,
  "confidence_level": "high",
  "rep_details": [
    {
      "index": 1,
      "start_ms": 1200,
      "peak_ms": 2750,
      "end_ms": 3900,
      "duration_ms": 2700,
      "source_sides": ["left", "right"],
      "is_standard": true,
      "flags": []
    }
  ],
  "quality_flags": ["camera_angle_unverified"]
}
```

指标定义如下：

- 最终次数：`max(left_event_count, right_event_count)`，并与 `rep_details` 长度保持一致；
- 单侧覆盖率：该侧四个必需关键点均可靠的帧数除以已处理帧数；
- 整体关键点覆盖率：至少一侧可靠的帧数除以已处理帧数；
- 双侧一致率：单调、一对一成功匹配的事件数量除以 `max(left_event_count, right_event_count, 1)`，结果限制在 0 到 1；
- `high`：整体覆盖率不低于 90%，且双侧一致率不低于 80%；
- `medium`：整体覆盖率不低于 70%，且双侧一致率不低于 50%，但未达到 `high`；
- `low`：其余仍能产生有效计数的情况。

置信度用于提示结果可靠程度，不修改 `total_count`。如果动作本身明确为单侧训练，未来应由该动作自己的规则器定义置信度；本期肩部推举按双侧动作处理。

## 9. 失败与资源清理

下列情况任务标记为 `failed`：

- 视频无法打开或没有可解码帧；
- PP-TinyPose 依赖或模型加载失败；
- 全程没有可用的人体关键点；
- 结果计数不满足持久化约束；
- 未捕获的推理或规则异常。

部分遮挡、画面抖动、左右结果差异和低覆盖率不直接失败。任务成功保存可用计数，并通过 `confidence_level`、动作标记和 `quality_flags` 告知调用方。

无论成功、失败或生成器提前关闭，都必须释放视频句柄并删除任务临时视频。异常信息继续使用现有脱敏失败原因，不返回本地路径、凭证或 traceback。

## 10. 任务执行与部署约束

- 动作分析 Worker 固定并发 1。
- 正式机器保持当前 2 vCPU，生产接入前把物理内存升级到 4 GiB，并保留现有 4 GiB Swap 作为 OOM 保护。
- 正常任务不应使用 Swap；发生持续 Swap 表示资源或实现异常。
- 现有 `MOTION_ANALYSIS_STALE_TIMEOUT_SECONDS=7200` 保留，可覆盖当前实测推算的 60 分钟视频约 74 分钟分析时间。
- 最终全帧实测为 430.125 秒，约为 300 秒视频时长的 1.43 倍；上线硬目标为不超过 2 倍。
- 本期不承诺实时处理，也不允许同一 Worker 并行分析多个视频。

最终 5 分钟全帧实测峰值 RSS 为 632,373,248 B，系统最低可用内存为 778,448,896 B，Swap 使用为零。服务器 `MemTotal` 仍只有 1,691,308,032 B（约 1.58 GiB），功能与算法验收通过但尚未达到 4 GiB 生产目标；内存扩容仍是生产接入前置条件，且不能替代流式改造。

## 11. 测试设计

### 11.1 单元测试

- 完整周期只计一次；开头和结尾半次动作不计数。
- 峰值突出度、上升/回落迟滞和 800 ms 去重边界。
- 5、10、30 FPS 与非恒定时间戳下，同一合成动作序列得到相同次数。
- 300 ms 内短暂缺失保留候选状态，超过 300 ms 放弃未完成周期。
- 最终次数取左右事件数较大值；锚点侧按事件数、平均覆盖率、左侧兜底确定，非锚点事件不会增加总数。
- 峰值差 400 ms 直接匹配；401–800 ms 的正时长事件按至少 50% 区间重叠扩展匹配，覆盖精确边界与非正时长拒绝。
- 双侧匹配只影响质量、一致率和置信度；单侧遮挡不漏计，清晰可见但不匹配产生质量标记。
- 幅度、肘角、节奏和置信度只影响标准性，不删除已形成的动作。
- 结果始终满足总数等式，动作时间按顺序且不重叠。

### 11.2 推理与任务集成测试

- 全帧配置逐个消费解码帧，不跳帧。
- 历史 v1 任务固定使用 5 FPS；v2 任务固定使用全帧且不受残留正数环境配置影响。
- 当前生产配置样例、benchmark 和 smoke 均不暴露正数 FPS 入口。
- 关键点迭代器为惰性，不在调用前读取完整视频。
- 正常完成、消费异常和提前关闭时均释放视频句柄。
- Celery 任务保存 `shoulder-press-v2` 和扩展结果字段。
- 现有分析创建、查询、失败重试和最近结果接口保持兼容。
- 60 分钟合成流验证检测器内存不随帧数线性增长。

### 11.3 真实视频验收

使用 SHA-256 为 `f4c7b1a4e1a7cdc192b32b73f6cb60600b02446d65f9aa471d34ee71458a78dd` 的 5 分钟视频：

- 验收输入 `manual_total_count` 必须固定为 90，且全帧计数必须等于 90；
- 相同环境重复运行结果必须一致；
- 报告必须且只能包含一档已完成的 `all_frames`，其 `sample_fps` 必须显式为 `null`，`decoded_frame_count` 与 `inferred_frame_count` 必须为相等的非负整数；字段缺失、不相等或出现 5/10 FPS 等采样证据时均为无效验收报告；
- `all_frames` 必须给出合法的 `result.total_count`，且 `count_error` 必须严格等于 `result.total_count - manual_total_count`；字段缺失、类型非法或计数不自洽时一律 fail-closed；
- 全帧总耗时不超过 600 秒；
- 应用进程峰值 RSS 低于 1.5 GiB；
- 正常运行 Swap 使用量保持为零；
- 服务器分析结束后删除输入视频和中间文件。

## 12. 上线与回退

1. 先在本地通过规则单元测试和任务集成测试。
2. 将候选版本部署到独立算法服务器，不改变公网端口和 SSH 安全设置。

回退只恢复算法应用，不回退数据库记录。历史 `MotionAnalysisJob` 通过各自的 `rule_version` 保持可审计。
