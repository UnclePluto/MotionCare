# 穿戴设备 OpenAPI 接入设计

> 状态：approved
> 日期：2026-07-23
> 范围：穿戴设备台账与患者绑定、厂商 OpenAPI 同步与远程操作、原始测量及日汇总、训练与健康页面升级、移除手工健康录入
> 关联：`docs/other/通信协议.pdf`、`docs/other/OpenAPI接口说明_V1.6.9.docx`、`specs/patient-rehab-system/prd.md`
> 明确不关联：CRF 模板、CRF registry、CRF 预览与导出
> 后续覆盖说明（2026-08-09）：设备入口名称与新建设备录入规则已由 `docs/superpowers/specs/2026-08-09-wearable-management-permission-design.md` 覆盖；入口统一为“设备管理”，新增设备只录入 15 位 IMEI，历史设备字段和数据继续保留。

## 1. 背景与目标

MotionCare 需要接入厂商穿戴设备，形成医院研究场景中的设备绑定、健康数据同步、远程操作和研究分析闭环。

本设计的目标是：

1. 医生可以把已入库设备绑定到全局患者，并快速验证设备通信是否正常。
2. 后台可以在设备型号能力允许时查询状态、下发非破坏性配置和主动测量命令。
3. 系统通过厂商 OpenAPI 获取步数、心率、血压、血氧，保留原始测量点并计算患者日汇总。
4. 穿戴健康与现有训练跟踪共同组成独立一级类目“训练与健康”。
5. 数据归属严格遵循患者与设备的绑定时间区间，设备解绑并重新分配后不得向新患者暴露旧患者数据。
6. 移除 Web 与微信小程序中的手工健康录入，健康数据以穿戴设备同步结果为准。

## 2. 已确认边界

### 2.1 接入方式

- 不实现设备 TCP 直连，不使用 `通信协议.pdf` 中的私有 TCP 上报链路。
- 设备继续向厂商官方平台上报，MotionCare 仅调用厂商 OpenAPI。
- 一期不依赖厂商 Webhook 或回调。
- 定时同步在每天凌晨 03:00（`Asia/Shanghai`）执行。
- 主动测量是定时同步之外的例外：命令成功后短轮询对应历史接口，尽快取得新测量点。

### 2.2 研究与医疗边界

- 穿戴数据用于研究记录、趋势查看和描述性分析。
- 不提供实时监护、急救告警、医学诊断或治疗建议。
- 不基于阈值自动产生临床结论。
- 不计算统计显著性。

### 2.3 CRF 硬边界

需求方已确认当前 CRF 内容不包含穿戴健康信息。本次接入：

- 不修改 CRF Word 模板。
- 不修改 CRF registry。
- 不修改 CRF 预览、导出、缺失字段校验和文件结构。
- 不增加健康附表。
- “训练与健康”页面不提供“CRF 关联数据”入口或提示。

穿戴健康属于研究数据，但不属于 CRF 数据。

### 2.4 权限

- 一期不细分设备管理员、医生等设备权限。
- 当前可进入医院管理后台的管理员和医生均可管理设备、绑定、解绑、同步和远程操作。
- 后端仍必须执行现有登录校验和医院数据范围过滤，不能只依赖前端隐藏按钮。

## 3. 核心业务概念

### 3.1 外部设备标识

厂商设备标识不写死为 IMEI，统一命名为 `external_device_id`，并记录 `identifier_type`。

设备唯一性为：

```text
provider + external_device_id
```

`identifier_type` 可以是 `imei`、`sn`、`device_id` 或后续厂商定义的其他类型。

### 3.2 设备固定简码

- 管理员先在设备台账录入真实厂商设备标识。
- 系统自动生成唯一的四位数字固定简码，允许前导零，例如 `0826`。
- 固定简码打印或粘贴在设备上，医生绑定时只需输入简码。
- 简码生成必须处理并发碰撞。
- 简码在设备生命周期内保持不变，不自动回收复用。
- 四位号码空间耗尽时明确阻止新增并提示扩容，不能静默复用旧码。

### 3.3 两种四位码必须区分

项目患者研究页同时存在两套机制：

| 名称 | 用途 | 生命周期 |
| --- | --- | --- |
| 小程序临时绑定码 | 把微信小程序连接到当前 `ProjectPatient` | 15 分钟有效，可撤销 |
| 设备固定简码 | 从设备台账定位穿戴设备并绑定全局患者 | 固定映射，不自动过期 |

页面文案必须使用完整名称，不能统一简称为“绑定码”。

### 3.4 绑定归属

- 穿戴设备绑定到全局 `Patient`，不绑定 `ProjectPatient`。
- 同一患者同一时刻最多一个有效设备绑定。
- 同一设备同一时刻最多绑定一个患者。
- 同一患者参与多个项目时，共用同一设备和同一份患者健康数据。
- 项目使用数据时只按项目研究时间范围进行筛选，不复制或重复绑定设备。

### 3.5 项目研究窗口

- `StudyProject.completed_at` 是可空的项目完结时间；项目通过完结动作首次进入 `archived` 时写入，重复完结不得刷新。
- 单个项目患者的研究窗口为半开区间 `[ProjectPatient.enrolled_at, StudyProject.completed_at)`；未完结项目的上界由合法查询日期范围或当前业务日决定。
- 原始测量按精确时间裁剪。患者日汇总和项目/分组聚合只统计完整落入窗口的 `Asia/Shanghai` 自然日；入组或完结发生在日中的边界日保守排除，步数不作部分日分摊。
- 项目完结不解绑设备、不停止同步，也不删除患者、训练、访视或 CRF 数据；完结后的新健康数据继续写入全局患者档案，但不进入已完结项目分析。

> 查询口径补充（2026-07-24）：同步状态仅统计当前绑定区间内的同步运行；指标状态取该区间最后一次真实运行状态，最近成功时间单独计算。原始趋势最多查询 31 个自然日且稳定分页；日汇总和研究汇总最多查询 366 日。项目汇总的心率、血压、血氧直接以已归属原始点计算，血压成对统计收缩压和舒张压；步数按完整研究日的有效日总量统计。

## 4. 系统架构

在现有 Django 单体中新增独立 `wearables` 应用，不拆分独立微服务。

```text
React 管理后台
    ├── 项目患者研究页：设备绑定/解绑
    ├── 设备台账：录入设备与生成固定简码
    └── 训练与健康：训练跟踪 + 穿戴健康
                │
                ▼
Django / DRF：apps.wearables
    ├── 设备与绑定服务
    ├── 厂商 OpenAPI 客户端
    ├── 同步与归属服务
    ├── 日汇总计算
    └── 远程命令与审计
                │
                ▼
Celery Beat 03:00 → Celery Worker → 厂商 OpenAPI
```

选择独立 Django 应用的原因：

- 设备台账、绑定区间、厂商通信、原始数据和命令审计属于同一业务边界。
- 与患者、项目、训练保持清晰外键关系，但不污染现有 `health` 手工录入模型。
- 后续增加第二家厂商时，可以在 `wearables.providers` 下扩展，不需要重写业务层。

## 5. 数据模型

### 5.1 `WearableDevice`

设备台账，建议字段：

- `provider`
- `external_device_id`
- `identifier_type`
- `model`
- `short_code`
- `enabled`
- `last_communication_at`
- `last_battery_level`
- `last_device_status`
- `last_status_checked_at`
- 创建人、更新人、创建时间、更新时间

约束：

- `provider + external_device_id` 唯一。
- `short_code` 唯一，格式为四位数字字符串。

设备状态是最近一次通信测试的快照，不把“在线”展示为“穿戴健康”页签标签。

### 5.2 `WearableBinding`

患者与设备的历史绑定区间：

- `patient`
- `device`
- `bound_at`
- `unbound_at`
- `bound_by`
- `unbound_by`
- `unbind_reason`

规则：

- `unbound_at IS NULL` 表示当前有效绑定。
- 服务层使用事务和行锁保证一个患者、一个设备各只有一条有效绑定。
- 历史绑定区间不得重叠。
- 绑定与解绑时间一旦形成数据归属后不得直接编辑；更正必须走受审计的管理流程。

### 5.3 `WearableMeasurement`

保存心率、血压、血氧原始测量点：

- `provider`
- `device`
- `binding`，允许为空
- `patient`，允许为空
- `metric_type`：`heart_rate`、`blood_pressure`、`blood_oxygen`
- `measured_at`
- `heart_rate`
- `systolic`
- `diastolic`
- `blood_oxygen`
- `source_fingerprint`
- `attribution_status`
- `raw_payload`

归属状态：

- `attributed`：测量时间落在唯一绑定区间内。
- `outside_binding`：测量时间不在任何绑定区间内。
- `ambiguous`：异常历史数据导致无法唯一确定绑定。

原始点按厂商、设备、指标、测量时间和规范化值生成指纹，重复补拉时幂等更新，不重复插入。

### 5.4 `WearableDailySource`

保存厂商按日返回的步数源数据：

- `provider`
- `device`
- `record_date`
- `steps`
- `distance`
- `calorie`
- `binding`
- `patient`
- `attribution_status`
- `raw_payload`

厂商步数接口只返回整日总量，不能按绑定时刻拆分。只有设备在 `Asia/Shanghai` 当天 00:00–24:00 全程属于同一患者时，步数才可归属。

以下场景的当日步数标记为 `ambiguous` 并排除：

- 当天中途首次绑定。
- 当天中途解绑。
- 当天设备从患者 A 改绑患者 B。

心率、血压、血氧有精确测量时间，仍按时间点归属，不受整日步数规则影响。

### 5.5 `WearableDailySummary`

患者日汇总，唯一键：

```text
patient + record_date
```

字段：

- 心率：`heart_rate_avg`、`heart_rate_min`、`heart_rate_max`、`heart_rate_count`
- 血压：`systolic_avg`、`diastolic_avg`、`blood_pressure_count`
- 血氧：`blood_oxygen_avg`、`blood_oxygen_min`、`blood_oxygen_max`、`blood_oxygen_count`
- 步数：`steps`
- 数据质量：`steps_attribution_status`、各指标最近同步状态
- 计算信息：`calculated_at`、`calculation_version`

日汇总只由有效原始数据计算，不允许人工编辑。

同一患者在一天内更换自己的设备时：

- 心率、血压、血氧可合并两个有效绑定区间内的测量点。
- 步数因无法拆分整日总量而留空，并标记不可归属。

### 5.6 同步与命令审计

同步至少包含：

- `WearableSyncCursor`：设备、指标、最近成功窗口结束时间。
- `WearableSyncRun`：计划时间、实际窗口、结果、返回数量、错误信息、重试次数。
- `WearableCommandLog`：设备、命令类型、请求参数、厂商返回码、状态、发起人、完成时间。

远程命令和定时同步必须可审计，但不得保存访问密钥和 Token 明文。

## 6. 数据归属与解绑

### 6.1 绑定

1. 医生在项目患者研究页输入设备固定简码。
2. 后端解析全局患者，检查患者与设备当前是否已有有效绑定。
3. 事务内锁定患者、设备和现有有效绑定。
4. 创建 `WearableBinding`。
5. 绑定成功后执行设备通信测试。
6. 页面分别展示：
   - “患者设备绑定成功”：表示 MotionCare 本地关系已建立。
   - “设备通信正常/异常”：表示厂商平台是否能联系设备。

通信异常不自动回滚已经成功的本地绑定，避免把网络状态误认为绑定关系失败。

### 6.2 通信测试

- 使用 `/api/location/get_location_info` 查询设备 ID、型号、在线状态、电量和最近通信时间。
- 不请求、不展示、不持久化位置、经纬度和轨迹。
- 型号能力允许时，医生可选择发送 `9018`“查找设备”命令，让设备响铃进行现场确认。
- 响铃是可选的物理确认，不作为绑定成功的必要条件。

### 6.3 解绑

1. 医生在项目患者研究页或设备操作抽屉发起解绑。
2. 二次确认明确提示：设备将停止为该患者归属新数据，历史研究数据不会删除。
3. 设置当前绑定的 `unbound_at`、`unbound_by` 和原因。
4. 立即禁止继续对该患者执行设备命令。
5. 后续拉取的数据按测量时间重新判断归属。

解绑后的“清理”含义是：

- 新患者看不到旧患者数据。
- 旧患者仍保留其绑定区间内的研究数据。
- 未绑定期间的数据不归属任何患者。
- 不物理删除已经形成研究依据的原始点和日汇总。

## 7. OpenAPI 数据同步

### 7.1 指标与接口

一期同步：

| 指标 | OpenAPI | 数据粒度 |
| --- | --- | --- |
| 心率 | `POST /api/heartrate/get_heartrate_bytime` | 原始测量点 |
| 血压 | `POST /api/bloodpressure/get_bloodpressure_bytime` | 原始测量点 |
| 血氧 | `POST /api/bloodoxygen/get_bloodoxygen_bytime` | 原始测量点 |
| 步数 | `POST /api/steps/get_steps_forday` | 设备日总量 |

OpenAPI 不返回日平均值。MotionCare 自行根据有效原始点计算日汇总。

### 7.2 每日任务

- Celery Beat 每天 03:00 生成同步任务。
- 每个存在当前有效绑定，或最近七天内刚解绑的设备每天一个调度任务，避免设备在凌晨任务前解绑后漏掉最后一段数据。
- 任务内部按心率、血压、血氧、步数分别调用接口；正常情况下是四次 HTTP 请求。
- 四类指标独立记录结果和重试，单个指标失败不回滚其他指标。
- 当日同步完成后，重算受影响日期的患者日汇总。

### 7.3 动态补拉窗口

不固定每次都拉七天，根据设备和指标的同步历史计算：

```text
start = max(
  最近七天相关绑定历史的最早开始时间,
  target_end - 7 天,
  最近成功窗口结束时间 - 24 小时重叠
)
```

若七天内存在未解决的失败窗口，`start` 可向前移动覆盖该窗口，但任何一次任务最多回看七天。

规则：

- 接口成功但返回空数组，也推进同步游标。
- 24 小时重叠用于接收厂商晚到或修正的数据。
- 原始数据幂等写入。
- 只重算实际受影响的日期。
- 超过七天仍未恢复的数据缺口保留在同步日志和完整性指标中，不无限回溯。

### 7.4 时区

- Django 保持 `USE_TZ = True`。
- 数据库存储有时区时间，统一规范为 UTC。
- 厂商返回的 UTC0 或 UTC8 时间必须经过明确解析器转换，禁止依赖服务器本地时区猜测。
- 患者日汇总、步数整日归属和页面日期均以 `Asia/Shanghai` 划分自然日。

## 8. 远程配置与主动操作

### 8.1 一期允许

- 查询设备状态、电量、型号、最近通信时间。
- 查找设备/响铃测试。
- 配置已验证型号支持的核心功能开关和测量/上传间隔。
- 单次主动心率、血压、血氧测量。
- 主动触发健康数据或当日步数同步。

### 8.2 一期排除

- 定位与轨迹。
- 电子围栏。
- 电话本、SOS 联系人。
- 拍照。
- 重启、关机、恢复出厂。
- 消息、提醒和其他非核心交互。

### 8.3 型号能力

- 不假设所有型号使用相同命令码。
- 在代码中维护“型号能力配置”，明确每个型号允许的命令、参数和返回解释。
- 未验证型号仍可登记、绑定并尝试标准历史数据同步。
- 未验证型号的远程配置和主动测量按钮禁用，并显示“该型号能力尚未验证”。

### 8.4 命令结果

厂商返回码按以下状态展示并写入审计：

| 返回码 | 解释 |
| --- | --- |
| `0` | 成功 |
| `1803` | 已进入发送/排队状态，继续轮询 |
| `1800` | 设备离线 |
| `1801` | 超时 |
| `1802` | 失败 |

主动测量在命令成功或排队后短轮询对应历史接口；超时只表示本次未在等待窗口内取得新点，不伪造测量值。

## 9. 页面与交互

### 9.1 设备台账

设备台账是基础管理入口，只负责：

- 录入厂商设备标识、标识类型和型号。
- 自动生成并展示设备固定简码。
- 查看当前绑定患者、最近通信和最近同步状态。
- 停用设备。

医生查看患者研究数据的主入口不是设备台账。

### 9.2 项目患者研究页

现有 T0/T1/T2 页签保持不变。

把当前“小程序绑定”区域升级为“患者接入”，包含：

1. 小程序绑定：生成和撤销 15 分钟临时绑定码。
2. 穿戴设备：输入设备固定简码、查看设备摘要、绑定、通信测试、可选响铃、解绑或更换。

虽然入口位于 `ProjectPatient` 页面，后端绑定对象仍是全局 `Patient`。

### 9.3 一级类目“训练与健康”

- 把现有侧边栏“训练追踪”更名并升级为“训练与健康”。
- 保留现有“训练记录”录入入口，不与本次页面合并。
- “训练与健康”患者列表可增加设备绑定状态、最近健康同步时间和数据完整率。
- 患者详情上方共享患者、项目、分组和研究时间范围。
- 详情页面内拆成两个页签：
  - `训练跟踪`
  - `穿戴健康`
- 页签名称旁不展示“设备在线”标签。

`训练跟踪` 页签完整保留：

- 处方完成情况。
- 训练趋势。
- 游戏表现统计。
- 最近训练记录。
- 录像与动作分析。

`穿戴健康` 页签展示：

- 设备摘要与最近通信状态。
- 日期、指标和图表间隔筛选。
- 心率、血压、血氧的原始点趋势。
- `原始 / 5 分钟 / 15 分钟 / 30 分钟 / 1 小时`动态聚合。
- 日汇总及数据完整性。
- 步数日总量，不绘制虚假的日内步数曲线。
- 设备通信测试、主动测量和主动同步。

### 9.4 研究汇总

一期支持：

- 单患者研究期趋势。
- 项目、分组、日期范围汇总。
- 样本量、有效数据日、均值、最小值、最大值、测量次数、数据缺失率和趋势。

不输出医学判断和统计显著性结论。

## 10. 移除手工健康录入

本设计明确替代旧的手工健康录入方案：

- 删除 Web `/health` 手工健康页面和路由。
- 删除 `/api/health/` 的新增、编辑和删除能力。
- 删除小程序“今日健康数据”页面、入口和 `/patient-app/daily-health/today/` 接口。
- 小程序首页不再返回或展示 `has_daily_health_today`。
- 删除旧 `DailyHealthRecord` 模型和表的业务使用。
- 通过显式 migration 删除旧表；不复用旧手工字段承载穿戴汇总。
- 新的穿戴日汇总不提供编辑接口。

项目当前没有需要迁移保留的手工健康数据。若实施前数据库检查发现已有记录，停止删除 migration 的生产执行并先由用户决定归档策略。

## 12. 异常与数据质量

- 固定简码不存在：不泄露厂商真实 ID，提示“未找到设备”。
- 设备已绑定其他患者：阻止绑定，显示脱敏患者信息并引导先解绑。
- 患者已有设备：阻止直接新增，要求使用“更换设备”流程。
- 状态查询失败：本地绑定关系与通信测试状态分别展示。
- OpenAPI 鉴权失败：停止继续请求并告警运维，不把错误解释为无数据。
- 厂商限流：指数退避，保留同步窗口，不推进失败指标游标。
- 厂商返回重复点：按指纹幂等。
- 厂商晚到数据：通过 24 小时重叠补齐。
- 测量点落在未绑定时段：保存为不可归属或隔离记录，不进入患者查询和日汇总。
- 同日换绑的整日步数：标记不可归属，不分摊、不猜测。
- 日汇总重算失败：原始点仍保留，汇总显示计算失败并可重试。

## 13. 安全与运维

- OpenAPI 地址、账号、密钥和 Token 通过环境变量或秘密管理注入。
- 日志对设备真实标识和 Token 脱敏。
- `raw_payload` 不保存位置等非本期数据。
- 远程命令必须记录发起人、设备、参数摘要、厂商返回和最终状态。
- Celery Beat 和 Worker 必须使用相同 `Asia/Shanghai` 业务日规则。
- 提供同步失败数量、最近成功时间、连续失败次数等运维指标。

## 14. 测试与验收

### 14.1 后端

- 四位固定简码格式、唯一性、并发碰撞和号码耗尽。
- 一患者一有效设备、一设备一有效患者、历史区间不重叠。
- 绑定、通信测试、响铃、解绑和更换设备。
- 测量点在绑定边界前、边界上、边界后及未绑定期间的归属。
- 同日换绑时点数据正确、整日步数排除。
- 四类指标解析、时区转换、重复补拉幂等。
- 动态补拉窗口最多七天，空结果推进游标，失败指标不推进。
- 日汇总均值、最小值、最大值、次数和重算。
- 未验证型号阻止远程配置与主动测量。
- CRF 预览和导出回归结果完全不因本功能变化。
- 手工健康 API 和患者端写接口移除。

- 设备台账录入和固定简码展示。

## 15. 已确认决策摘要

1. 使用厂商 OpenAPI 定时拉取，不接 TCP。
2. 新增单体内独立 `wearables` Django 应用。
3. 设备真实标识抽象为 `external_device_id`。
4. 设备使用固定四位简码，项目患者页输入简码绑定。
5. 绑定属于全局患者，项目按研究时间范围使用数据。
6. 每天 03:00 同步，动态补拉，最多回看七天。
7. 保留原始测量点，生成患者日汇总，不建固定小时汇总表。
8. 日内图表按查询动态聚合。
9. 解绑保留旧患者研究数据，新患者只见新绑定区间数据。
10. 同日换绑的整日步数因无法拆分而排除。
11. 远程命令按设备型号能力开放，排除破坏性与非核心命令。
12. “训练追踪”升级为一级类目“训练与健康”，详情拆成两个页签。
13. 移除 Web 和小程序手工健康录入。
14. CRF 完全不修改，不包含穿戴健康信息。
