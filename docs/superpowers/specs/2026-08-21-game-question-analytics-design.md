# 游戏逐题数据与长期统计设计

## 背景

MotionCare 的六款认知游戏已经通过微信小程序完成真实游玩、整场计分和训练记录上传。当前小程序会把部分每轮信息写入 `TrainingRecord.form_data.raw_detail.rounds`，其中已经包含 `response_ms` 和 `correct`，但存在三个问题：

1. 后端只把 `rounds` 当普通 JSON 保存，没有稳定的逐题数据契约和数据库约束。
2. 现有 `response_ms` 由墙上时钟直接相减，暂停期间可能被计入，不能稳定代表有效作答时间。
3. 医生端只展示整场得分、正确率和错误数，无法查看单场逐题明细或患者长期答题速度趋势。

本设计在不改变处方和训练记录主链路的前提下，把逐题结果提升为可校验、可查询的正式研究数据。

## 已确认决策

1. 覆盖当前全部六款认知游戏，使用统一逐题核心结构。
2. `TrainingRecord` 继续代表一次完整训练会话；新增逐题子模型，不新增独立 `GameSession`。
3. 每题完成时间采用“题目进入可作答状态到最终提交答案”的有效作答时间，排除展示、语音、暂停和答后反馈。
4. 会话结束时尚未完成的当前题直接丢弃，不创建逐题记录。
5. 拼图按完成一幅拼图记录一题，额外记录实际方块交换次数，不记录普通点击次数。
6. 小程序在整场结束时批量上传训练记录与逐题结果，不逐题请求服务器。
7. 新增客户端会话 UUID，使整场训练和补传具备服务端幂等性。
8. 医生端沿用现有“训练追踪详情”入口，提供近 7 天、近 30 天和自定义日期范围。
9. 可识别的历史 `raw_detail.rounds` 迁移为正式逐题数据；异常项跳过，原始 JSON 保持不变。
10. 拼图不参与综合正确率；拼图长期统计以完成量、完成时间和交换次数为主。

## 目标

- 可靠保存每个已完成题目的有效作答时间和正确性。
- 为拼图保存完成时间和实际交换次数。
- 保证弱网补传不会重复创建训练场次或逐题数据。
- 在医生端查看单场逐题明细。
- 按项目患者、日期、游戏和难度统计长期正确率与作答速度趋势。
- 尽可能纳入已有合法逐题历史数据，并显式保留历史计时口径信息。

## 非目标

- 不新增独立游戏会话体系或改变 `TrainingRecord` 的会话语义。
- 不实现逐题实时上报、实时监控或游戏中途跨设备恢复。
- 不记录每一次普通点击、点击轨迹、坐标或完整操作事件流。
- 不新增一级“游戏数据统计”页面。
- 不做跨项目合并统计；同一患者在不同项目中的数据继续按 `ProjectPatient` 隔离。
- 不新增逐题数据导出功能。
- 不修改六款游戏的玩法、难度规则或整场计分公式，除非逐题权威汇总校验要求修正明显不一致。

## 方案选择

### 采用：关系表保存逐题结果，整场批量上传

新增 `GameQuestionResult`，作为 `TrainingRecord` 的子记录。小程序在内存中累计已完成题目，整场结束后一次上传；后端在同一事务中创建训练记录和逐题结果。

该方案相比继续解析 JSON，能够提供字段约束、幂等写入、权限清晰的明细查询，以及更稳定的日期、游戏、难度聚合。相比逐题实时上报，它不引入题目级离线队列、乱序和高频请求。

### 未采用：只扩展 `raw_detail.rounds`

改动较少，但长期统计依赖应用层逐条解析 JSON，数据质量、索引和查询维护性不足。

### 未采用：每完成一题立即上传

可以近实时落库，但弱网、页面隐藏、重复请求和题目顺序恢复成本明显高于当前需求。

## 数据模型

### `TrainingRecord` 扩展

新增可空 `client_session_id` UUID 字段和可空 `client_payload_fingerprint` SHA-256 十六进制字段：

- 新版小程序必须为每次实际游戏训练生成一个 UUID。
- 同一 UUID 只允许对应一条训练记录。
- 历史记录和未升级客户端创建的记录允许为空。
- 首次写入时，后端对患者、处方动作和标准化后的训练/逐题语义内容计算指纹并保存。
- 指纹排除后端派生汇总字段，以及 `raw_detail.upload_mode`、`retry_count`、`total_retry_count` 这三个传输重试元数据；补传改变这些字段不构成训练内容冲突。
- 幂等重传时，后端比较 UUID 和语义指纹；完全一致返回已有记录，内容冲突返回 `409`。已保存记录不因幂等重传改写传输元数据。

### `GameQuestionResult`

字段定义：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `training_record` | ForeignKey | 所属训练记录，级联删除 |
| `question_index` | PositiveInteger | 本场已完成题目的连续序号，从 1 开始 |
| `game_code` | CharField | 游戏编码快照 |
| `difficulty` | CharField | 本题实际难度 |
| `response_duration_ms` | PositiveInteger | 有效作答时间，毫秒 |
| `is_correct` | Boolean | 是否正确；超时题为 `false` |
| `result_type` | Choice | `answered` 或 `timeout` |
| `swap_count` | PositiveInteger/null | 拼图实际交换次数；其他游戏为空 |
| `capture_version` | Choice | `legacy_wall_clock_v0` 或 `active_response_v1` |

约束与索引：

- 同一 `training_record + question_index` 唯一。
- `question_index` 必须大于 0。
- `response_duration_ms` 和 `swap_count` 不得为负。
- `timeout` 必须对应 `is_correct = false`。
- 新版拼图完成题必须提交 `swap_count`，必须为 `answered + is_correct = true`。
- 新版非拼图题不得提交 `swap_count`。
- 历史拼图可能无法还原交换次数，允许 `capture_version=legacy_wall_clock_v0` 时为空。
- 为训练记录外键、`game_code` 和 `difficulty` 建立聚合所需索引。

不把题目内容、正确答案、患者选择或完整点击轨迹复制到新关系表。旧记录中的相关原始 JSON 保持不变，但新版客户端只提交本期统计所需字段。

## 统一“题目”口径

| 游戏 | 一题的定义 | 正确性 | 时间起点 | 特殊指标 |
| --- | --- | --- | --- | --- |
| 颜色顺序记忆 | 完整复现一段颜色序列 | 整段是否一致 | 序列展示结束、允许输入 | 无 |
| 图案顺序记忆 | 完整复现一段图案序列 | 整段是否一致 | 序列展示结束、允许输入 | 无 |
| 反应抑制 | 对一组数字完成一次选择 | 是否选择不同数字 | 题目和选项可点击 | 无 |
| 分类转换 | 按当前规则完成一次选择 | 是否选择正确分类 | 题目和选项可点击 | 无 |
| 声音辨别 | 试听完成后完成一次选择 | 是否选择目标声音 | 目标声音播放结束、允许选择 | 无 |
| 拼图 | 完成一幅拼图 | 完成即为正确 | 预览结束、允许交换 | 实际交换次数 |

整场计时结束或用户提前结束时，如果当前题尚未形成最终判定，则丢弃该题。已经因单题超时形成判定的题目记录为 `timeout + is_correct=false`。

## 小程序计时与采集

### 共用有效时间计时器

六款游戏复用一个与 React/Taro 页面状态解耦的纯逻辑计时器：

- `start(now)`：进入可作答状态。
- `pause(now)`：累计本段有效时间并冻结。
- `resume(now)`：从冻结值继续。
- `finish(now)`：返回累计有效毫秒数并终止。
- `discard()`：会话结束时丢弃当前题。

计时器使用单调、可注入的时间来源，测试不依赖真实等待。题目展示、序列预览、声音播放、暂停和答后反馈不进入有效作答时间。

### 拼图交换次数

拼图进入可操作状态后，每次两个方块实际发生位置交换时累计一次。以下情况不累计：

- 只选择第一个方块。
- 点选同一个方块而没有交换。
- 预览或暂停期间被拦截的点击。
- 页面按钮和其他非方块交互。

### 整场收口

小程序只把已完成题目追加到本场内存列表。结束时生成：

- 现有训练会话摘要。
- `client_session_id`。
- `question_results`。

待补传缓存保存完全相同的 UUID 和逐题列表。小程序意外退出且尚未执行整场结束时，本次不上传也不恢复，这是现有游戏会话语义的延续。

## 写入 API

继续使用：

```text
POST /api/patient-app/training-records/
```

新增请求字段示例：

```json
{
  "client_session_id": "de4580ae-4f62-4a63-bf64-bc2cde971955",
  "question_results": [
    {
      "question_index": 1,
      "game_code": "game-executive-inhibition",
      "difficulty": "中等",
      "response_duration_ms": 2380,
      "is_correct": true,
      "result_type": "answered",
      "swap_count": null
    }
  ]
}
```

### 校验规则

- 只有游戏动作可以提交 `question_results`。
- `game_code` 必须匹配当前处方动作的 `source_key`。
- 新版游戏请求的 `question_index` 必须从 1 连续递增且不得重复。
- 单次最多提交 2,000 个逐题结果；单题有效作答时长不得超过 3,600,000 毫秒。
- 全部逐题有效时长之和不得超过 `session_duration_seconds * 1000 + 1000` 毫秒；额外 1 秒只用于兼容整场秒数取整误差。
- `timeout`、正确性和拼图字段遵守模型规则。
- 空列表合法，表示整场结束前没有完成任何题目。
- 后端从逐题数据重新计算 `completed_units`、`correct_units`、`accuracy_rate` 和 `error_count`，不信任客户端对这些指标的汇总。
- 训练记录与全部逐题记录在一个事务中创建；任一题非法时整场不落库。

### 响应和幂等

- 首次成功创建返回 `201`。
- 完全一致的 `client_session_id` 重传返回原训练记录和 `200`。
- UUID 相同但患者、处方动作或标准化语义内容不同返回 `409`；仅传输重试元数据变化仍返回原记录和 `200`。
- 没有 UUID 的旧客户端维持现有非幂等行为。

### 旧客户端兼容

旧版小程序仍可提交 `form_data.raw_detail.rounds`。当顶层 `question_results` 缺失时，后端尝试从合法的 `rounds` 生成 `GameQuestionResult`；无法识别的题目不阻塞旧版整场训练记录创建。顶层 `question_results` 存在时以它为唯一权威来源，不再同时解析 `rounds`。

## 历史数据迁移

数据迁移扫描游戏类 `TrainingRecord.form_data.raw_detail.rounds`：

1. 只接受正整数且不重复的 `round_index`、非负整数 `response_ms`、布尔 `correct`。
2. `result=timeout` 映射为 `result_type=timeout`；其他已答题映射为 `answered`。
3. 游戏编码优先取题目明细，缺失时取整场 `raw_detail.game_code` 或处方动作 `source_key`。
4. 难度优先取题目明细，缺失时取整场 `form_data.difficulty`。
5. 历史题目标记为 `capture_version=legacy_wall_clock_v0`；其时长可能包含旧实现中的暂停时间，医生端应以“历史估算”解释。
6. 无法还原的拼图交换次数保持为空。
7. 若训练记录已经有逐题子记录则跳过，保证迁移幂等。
8. 异常题目跳过；原 `form_data` 和 `raw_detail` 永不删除或改写。

## 医生端查询 API

逐题统计独立于现有训练追踪详情主体，避免页面初次加载下载全量题目。

### 聚合接口

输入：

- `patient_id` 和现有选中的 `project_patient_id`。
- 时间范围：`7d`、`30d`，或 `start_date + end_date`。
- 可选 `game_code`、`difficulty`。

输出：

- 完成题数、正确率、平均有效作答时间、中位有效作答时间。
- 按游戏聚合的训练场次、完成题数、正确率、平均/中位时间。
- 单游戏按日期的正确率和中位作答时间趋势。
- 拼图完成数、平均/中位完成时间、平均交换次数。
- 合法历史估算题目的数量，供界面展示数据口径说明。

所有统计以 `TrainingRecord.training_date` 归入日期。超时题进入错误分母；未完成题不存在，不进入任何统计。拼图不进入综合正确率，防止“完成即正确”人为抬高指标。

### 单场逐题接口

按 `TrainingRecord` ID 分页返回逐题结果，默认每页 50 条、最多每页 200 条。仅游戏训练可用；无逐题数据返回空分页结果而不是错误。

两个接口都必须复用现有训练追踪的医生/管理员权限与 `ProjectPatient` 行级范围。服务端先校验训练记录属于当前可访问患者和项目关系，再读取逐题数据，禁止仅凭逐题或训练记录 ID 直接查询。

## 医生端交互

沿用“训练追踪详情”中的“游戏表现统计”区域：

1. 筛选器提供“近 7 天”“近 30 天”“自定义日期”，默认近 30 天。
2. 自定义日期使用日期范围控件，开始日期不得晚于结束日期。
3. 提供游戏和难度筛选。
4. 汇总卡片展示完成题数、正确率、平均和中位有效作答时间。
5. 分游戏表格展示训练场次、完成题数、正确率、平均和中位时间。
6. 单游戏趋势图按日期展示正确率和中位作答时间；一次只展示一个游戏，避免不同玩法混合后失真。
7. 拼图展示完成数、平均/中位完成时间和平均交换次数，正确率显示“无需统计”。
8. 最近训练记录中的游戏场次增加“查看逐题”操作，抽屉分页展示题号、正确/错误/超时、有效作答时间和难度；拼图额外显示交换次数。
9. 历史计时数据存在时展示简短口径提示，避免把旧墙上时钟时长误读为严格有效时间。

逐题统计接口失败只影响本区域；训练追踪的处方、视频、穿戴等其他区域继续可用。旧训练没有逐题数据时显示“该场训练暂无逐题明细”。

## 错误处理

- 逐题字段非法：返回字段级 `400`，事务回滚。
- UUID 内容冲突：返回 `409`，不覆盖已有记录。
- 处方已更新：沿用当前“处方已更新，请返回当前处方重新进入”的错误。
- 自定义日期非法：返回 `400`，前端保留已有统计并提示修正日期。
- 统计空结果：展示空状态和 0/无数据，不伪造百分比或时间。
- 单场明细接口失败：抽屉展示可重试错误，不关闭主页面。

## 性能与数据量边界

- 聚合由后端执行，前端不下载全量逐题数据自行计算。
- 单场明细分页返回。
- 查询始终先限定一个 `ProjectPatient` 和日期范围，再按游戏、难度过滤。
- 历史迁移批量读取和写入，避免逐条数据库往返。
- 单次写入最多 2,000 个逐题结果、单题最多 3,600,000 毫秒；接口同时遵守部署层和 Django 现有请求体大小限制。
