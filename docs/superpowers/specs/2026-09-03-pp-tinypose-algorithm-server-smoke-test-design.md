# PP-TinyPose 独立算法服务器冒烟测试设计

## 1. 背景与目标

MotionCare 已具备肩部推举视频分析的业务代码：PP-TinyPose 输出人体关键点，肩部推举规则层再计算总次数、标准次数、不标准次数和每次动作时间段。当前生产镜像未安装动作分析可选依赖，分析任务也尚未隔离到独立 Worker。

本阶段先在独立阿里云 ECS 上验证 CPU 原生运行能力，不立即连接生产 PostgreSQL、Redis、医生端接口或七牛对象存储。测试使用用户提供的本地视频，通过安全复制上传到算法服务器，完成三种采样模式对照并输出资源与算法报告。测试结果用于决定是否扩容实例，以及正式接入时采用的采样策略。

## 2. 已确认决策

1. 算法服务器采用宿主机原生部署，不使用 Docker。
2. 操作系统固定为 Ubuntu 24.04 LTS x86-64，使用系统 Python 3.12 创建独立虚拟环境。
3. 当前 2 vCPU、约 2 GiB 物理内存的实例先做测试，不预先扩容。
4. 增加 4 GiB Swap 作为 OOM 保护；Swap 不是目标运行内存，也不作为性能充足的证据。
5. 推理设备固定为 CPU，任务并发固定为 1。
6. 使用 `PP-TinyPose_128x96`，复用 MotionCare 当前肩部推举规则层，不另写一套计数算法。
7. 测试输入改为本地文件 `IMG_0383_SDR_5min.mp4`，本阶段不接入七牛。
8. 同一视频执行 5 FPS、10 FPS、原始全部帧三组对照。
9. 技术可运行性是首轮硬验收；算法准确度先与人工观察对照，不因单个样例直接修改业务阈值。
10. 冒烟阶段不启动常驻服务，不开放公网端口。

## 3. 范围

### 3.1 本阶段包含

- 恢复并验证算法服务器 SSH 密钥登录，关闭 SSH 密码认证。
- 创建专用无登录系统用户和隔离运行目录。
- 创建 4 GiB Swap，并验证重启后可用。
- 安装 FFmpeg、Python 3.12 虚拟环境及固定版本的 CPU 推理依赖。
- 将 MotionCare 当前分析代码部署到服务器，不携带项目数据库数据或生产密钥。
- 将测试视频安全复制到服务器临时输入目录。
- 校验视频哈希、编码、分辨率、时长、帧率与大小。
- 执行 5 FPS、10 FPS、全帧三组推理。
- 输出脱敏 JSON 报告和简洁的人类可读汇总。
- 分析结束后删除服务器上的测试视频和中间帧，保留模型缓存与报告。
- 根据实测结果给出内存、CPU 和采样模式建议。

### 3.2 本阶段不包含

- 不连接七牛 Kodo，不保存七牛 AK/SK 或临时签名 URL。
- 不连接生产 PostgreSQL 或 Redis。
- 不修改 Celery 路由，不部署正式动作分析 Worker。
- 不修改医生端接口、页面或任务状态流转。
- 不支持除肩部推举之外的其他动作。
- 不把单段样例结果解释为医学诊断或模型临床有效性证明。
- 不因一个视频直接调整肩部推举规则阈值。
- 不运行 PaddleX 高性能推理插件，不引入其授权与激活流程。

## 5. 服务器目录与权限边界

运行根目录固定为：

```text
/opt/motioncare-analysis/
├── app/          # 与实施 commit 对齐的 MotionCare 分析代码
├── venv/         # Python 3.12 虚拟环境
├── model-cache/  # PP-TinyPose 模型缓存
├── input/        # 测试输入，完成后清空
├── tmp/          # 临时文件和中间产物，完成后清空
├── reports/      # 脱敏 JSON 与文本报告
└── logs/         # 不含视频路径外部凭证的运行日志
```

权限规则：

- root 只负责系统包、Swap、目录和系统用户初始化。
- 推理使用无登录权限的 `motioncare-analysis` 系统用户。
- `app`、`venv`、`model-cache`、`input`、`tmp`、`reports`、`logs` 仅允许 root 和该系统用户访问。
- 测试视频权限固定为 `0600`，不得由其他本机用户读取。
- 冒烟阶段不创建 systemd 常驻服务，不监听 TCP 端口。

## 6. 软件运行环境

虚拟环境使用 Python 3.12，并固定直接依赖版本：

- `paddlepaddle==3.3.0` CPU 版
- `paddlex[cv]==3.7.2`
- `opencv-python-headless>=4.10,<5.0`
- MotionCare backend 当前包及其必要依赖

系统依赖至少包含：

- `ffmpeg` / `ffprobe`
- `python3-venv`
- `ca-certificates`

安装完成后必须分别验证：

- `paddle.utils.run_check()` 成功；
- PaddleX 能创建 `PP-TinyPose_128x96` CPU 模型；
- FFmpeg 能读取测试视频；
- OpenCV 能打开视频并读取首帧；
- 模型首次下载后能从持久模型缓存再次加载。

## 7. 分析器边界

冒烟分析器由三个清晰单元组成：

1. **视频探测器**：读取媒体元数据、计算 SHA-256、拒绝无法解码或元数据异常的输入。
2. **关键点提取器**：复用 `apps.training.pose_inference` 的 PP-TinyPose 适配逻辑，以明确的 CPU 设备运行，并支持固定 FPS 与全帧两类采样策略。
3. **动作规则器**：复用 `apps.training.analysis.analyze_shoulder_press_keypoints`，只消费带时间戳的标准化关键点帧。

命令行编排层只负责参数、阶段计时、内存采样、报告汇总与清理，不复制关键点转换或肩部推举规则。

## 8. 三组对照策略

同一个视频下载或复制一次，模型加载一次并使用首个有效样本预热。三组分析依次执行，每组重新打开视频，组间释放关键点帧列表并执行垃圾回收，模型实例和模型缓存继续复用。

### 8.1 5 FPS 基线

- 每 200 ms 左右选择一帧进入 PP-TinyPose。
- 预计推理约 1,500 帧。
- 对应 MotionCare 当前默认行为。

### 8.2 10 FPS 对照

- 每 100 ms 左右选择一帧进入 PP-TinyPose。
- 预计推理约 3,000 帧。
- 用于观察更密采样是否改善动作起止时间或计数。

### 8.3 原始全部帧对照

- 每个成功解码的视频帧都进入 PP-TinyPose，不用容器平均 FPS 近似全帧。
- 预计推理约 8,929 帧。
- 保留每帧真实时间戳，兼容平均帧率不是整数的输入。

全帧不是默认更准确。当前规则包含连续帧确认与最低置信度判断，采样密度变化可能放大关键点抖动或低置信度偶发帧。因此三组必须分别输出原始规则结果，不在本轮自动调阈值。

## 9. 执行数据流

```text
本地测试视频
  → SCP 到服务器 input 目录
  → 权限和 SHA-256 校验
  → ffprobe / OpenCV 媒体预检
  → CPU 模型加载与预热
  → 5 FPS 推理及规则分析
  → 释放该组关键点数据
  → 10 FPS 推理及规则分析
  → 释放该组关键点数据
  → 资源允许时执行全帧推理及规则分析
  → 写入脱敏报告
  → 删除服务器输入视频与中间文件
  → 从服务器下载报告到本地留档
```

## 10. 报告契约

JSON 报告必须包含：

- 报告格式版本；
- 运行开始与结束时间；
- Git commit、Python、PaddlePaddle、PaddleX、OpenCV 和 FFmpeg 版本；
- CPU 型号、vCPU 数、物理内存、Swap 总量；
- 视频 SHA-256、字节数、时长、编码、分辨率、标称和平均帧率；
- 模型名、设备和模型加载/预热耗时；
- 每种模式的目标采样策略、实际解码帧数、实际推理帧数；
- 每种模式的推理耗时、整体耗时、平均每推理帧耗时；
- 每种模式执行期间的峰值 RSS、峰值系统内存和峰值 Swap 使用量；
- `total_count`、`standard_count`、`nonstandard_count`、`rep_details` 和 `quality_flags`；
- 阶段状态：`completed`、`failed` 或 `skipped_for_resource_safety`；
- 失败阶段与脱敏错误摘要。

报告不得包含：

- 患者身份信息；
- 本地原始绝对路径；
- SSH 信息；
- 对象存储凭证或签名 URL；
- Python traceback 中可能出现的敏感路径。

人工总次数允许在运行后补录。未提供人工标签时，报告必须明确写为 `not_provided`，不得伪造或用模型输出代替人工真值。

## 11. 资源保护

- 创建 4 GiB Swap 文件，并写入 `/etc/fstab` 保证重启后生效。
- 推理并发严格为 1，不并行运行三个采样模式。
- 开始前检查根分区剩余空间，低于 10 GiB 时拒绝复制和分析视频。
- 开始前记录空闲内存与 Swap；每组运行期间持续采样进程 RSS 和系统 Swap。
- 5 FPS 或 10 FPS 若发生 OOM、进程被杀、无法分配内存或系统失去响应迹象，则不执行更高负载模式。
- 10 FPS 完成后若可用内存与 Swap 余量不足以继续安全运行，全帧模式标记为 `skipped_for_resource_safety`，不把跳过误报为算法失败。
- 全帧失败不覆盖已完成的 5 FPS、10 FPS 报告。
- 不通过降低模型精度、替换模型或静默减少视频区间来伪造通过。

## 12. 清理与失败恢复

- 输入视频、临时文件和中间帧必须置于 `input` 或 `tmp`，不得散落在 root 主目录。
- 正常完成、Python 异常、信号中断均进入清理路径。
- 报告先写临时文件，完整落盘后原子替换为最终报告，避免留下看似成功的半份 JSON。
- 失败报告保留已完成阶段、资源采样和安全错误摘要。
- 输入视频删除后验证服务器上不存在同 SHA-256 的测试副本。
- 模型缓存、虚拟环境、应用代码、脱敏报告和日志可以保留。
- 若安装过程失败，不删除系统日志；虚拟环境允许整体重建，不在损坏环境上继续叠加安装。

## 13. 测试与验收

### 13.1 技术硬验收

- SSH 密钥登录有效，密码登录关闭。
- Swap、目录、用户和权限符合本设计。
- PaddlePaddle 自检通过。
- PP-TinyPose CPU 模型加载和预热通过。
- 测试视频元数据与本设计记录一致，SHA-256 完全匹配。
- 5 FPS 和 10 FPS 两组均完成关键点提取、规则分析和报告写入。
- 全帧运行完成，或因明确记录的资源安全条件被跳过/失败；该结果用于扩容决策，不影响前两组技术通过状态。
- 三组实际推理帧数与采样策略相符。
- 输入视频和临时文件被清理，脱敏报告保留。

### 13.2 算法观察项

- 三组总次数是否一致；
- 三组与人工总次数的差异；
- 标准/不标准数量及标记差异；
- 动作起止时间的偏移；
- 全帧是否因瞬时抖动产生额外状态事件；
- 全帧是否因偶发低置信度帧增加 `low_confidence`；
- 10 FPS 相比 5 FPS 是否带来可见收益。

首轮不设置标准/不标准准确率硬阈值。只有在获得多段已人工标注的视频后，才能启动规则校准设计。

### 13.3 资源决策

- 若 5 FPS 即发生 OOM，停止测试并优先扩容物理内存。
- 若 5 FPS、10 FPS 可完成但频繁大量使用 Swap，技术可行但不建议以当前规格正式运行。
- 若全帧显著变慢且计数无改善，正式接入保持 5 FPS 或 10 FPS。
- 若全帧明显改善计数，后续先将规则去抖改为按时间语义，再评估正式采用全帧。
- 正式 Celery Worker 的目标规格在本报告基础上确定；冒烟通过不自动代表 2 GiB 适合生产。

## 14. 后续演进边界

冒烟完成并选定采样策略后，正式接入另行设计和实施：

1. 构建专用 `motion-analysis` Celery 队列。
2. 算法服务器只消费该队列，默认并发 1。
3. 通过受保护网络连接生产 Redis/PostgreSQL，禁止直接公开数据库端口。
4. 由正式 Worker 获取七牛私有下载地址并下载临时视频。
5. 复用本次验证过的虚拟环境、模型缓存和分析器边界。
6. 根据报告决定是否先扩容至 4 vCPU / 8 GiB。

上述正式接入不属于本次冒烟实施计划，避免在基础可运行性尚未验证前扩大生产变更面。
