# 五运动动作正式视频与统一录像跟练设计

## 1. 背景

动作库已固定预置五个运动动作，但正式教学视频尚未完整接入。当前只有肩部推举具备独立动作预览、前置摄像头、示范视频画中画、五秒分片录像、后台上传、服务端合并、七牛发布、训练记录和医生审阅闭环；其余四个运动动作仍进入通用手工训练记录页。

本次提供的五个正式 MP4 均已完成文件与画面抽检：视频为竖屏 1080×1920、H.264 + AAC，时长约 10–15 秒，内容分别与高抬腿摆臂、坐站转移、坐姿划船、腿部后踢和肩部推举对应。肩部推举必须废弃旧示范源并使用本次正式视频。

本设计将肩部推举专用录像能力泛化为通用运动视频跟练引擎。五个正式运动动作均采用相同患者流程并上传患者录像；AI 动作分析保持独立、可插拔，本期只保留肩部推举现有分析能力，其余动作后续逐个接入。

本设计覆盖并替代 `2026-08-09-wechat-shoulder-press-preview-pip-design.md` 中“不扩展到其它运动动作”的非目标边界，不回退其中已经落地的录像可靠性、安全和交互决策。

## 2. 已确认决策

1. 五个正式运动动作全部支持动作说明、独立视频预览、前置摄像头与示范视频画中画、按处方时长录像、五秒分片、断点补传、服务端合并、七牛发布、训练记录和医生审阅。
2. 肩部推举的旧教学视频必须换成此次正式素材。
3. 教学视频继续存储在现有七牛私有空间；数据库保存稳定对象 Key，播放时由后端动态生成短期 HTTPS 签名地址。
4. 五个动作库记录、所有生效处方动作快照和所有历史处方动作快照统一回填正式视频对象 Key，不要求医生重新开具处方。
5. 审核演示模式也展示五个正式运动动作，允许动作预览和摄像头跟练体验，但禁止录像、文件生成、上传和训练记录持久化。
6. 审核演示模式的五个运动动作统一按 10 分钟本地计时，允许提前结束。
7. 真实患者单次运动录像的业务上限为 30 分钟；各动作按处方实际时长结束，不强制练满 30 分钟。
8. 五个正式运动动作不得再绕过录像闭环进入通用手工打卡页。
9. 录像主流程与 AI 分析解耦。分析器按动作编码注册；本期只有肩部推举可发起分析，其余动作只积累标准录像和训练数据。
10. 采用通用运动视频跟练引擎，不复制五套流程，也不继续让新逻辑依赖肩部推举专用命名。

## 3. 目标

- 将五个正式教学视频可靠、可审计、幂等地上传至七牛私有空间。
- 以不会过期的对象 Key 作为动作库和处方快照的媒体真相来源。
- 保持现有 API 的 `video_url` / `video_url_snapshot` 响应兼容，同时改为动态签名值。
- 为五个正式运动动作提供一致的小程序录像跟练体验。
- 复用现有分片、缓存保护、失败恢复、合并、发布、清理和医生审阅能力。
- 保留旧肩部推举路由与待上传本地会话兼容，避免小程序升级导致录像丢失。
- 建立可插拔分析器边界，为后续逐动作增加 AI 分析做好接口准备。

## 4. 非目标

- 本期不为高抬腿、坐站转移、坐姿划船或腿部后踢实现 AI 评分算法。
- 不改变游戏训练流程。
- 不允许患者选择、替换或上传教学视频。
- 不开放任意七牛对象 Key 的签名接口。
- 不修改患者训练录像的既有私有访问、清理与解绑语义。
- 不把教学视频打包进小程序代码包。
- 不在本次范围内设计视频内容运营后台或多版本切换界面。

## 5. 正式视频映射与上传

### 5.1 固定映射

| 动作编码 | 动作名称 | 本地文件 | 七牛对象 Key |
| --- | --- | --- | --- |
| `motion-aerobic-high-knee` | 椰林步道模拟（原地高抬腿+摆臂） | `docs/other/运动处方/高抬腿+摆臂/高抬腿+摆臂 动作教学.mp4` | `motion-action-videos/v1/motion-aerobic-high-knee.mp4` |
| `motion-balance-sit-stand` | 坐站转移训练 | `docs/other/运动处方/坐站转移/坐姿转移 动作教学.mp4` | `motion-action-videos/v1/motion-balance-sit-stand.mp4` |
| `motion-resistance-row` | 坐姿划船 | `docs/other/运动处方/坐姿划船/坐姿划船 动作教学.mp4` | `motion-action-videos/v1/motion-resistance-row.mp4` |
| `motion-resistance-leg-kickback` | 腿部后踢 | `docs/other/运动处方/腿部后踢/腿部后踢 动作教学.mp4` | `motion-action-videos/v1/motion-resistance-leg-kickback.mp4` |
| `motion-resistance-shoulder-press` | 肩部推举 | `docs/other/运动处方/肩部推举/动作教学.mp4` | `motion-action-videos/v1/motion-resistance-shoulder-press.mp4` |

对象路径必须版本化。未来正式换片使用 `v2` 等新 Key，不覆盖已发布的 `v1` 对象；是否回填历史处方必须另行确认。

### 5.2 上传命令

新增显式管理命令：

```bash
python manage.py upload_motion_action_videos --source-root <运动处方目录>
```

命令接收素材根目录并执行固定映射上传。它必须：

- 在上传前验证五个文件全部存在且均为普通文件。
- 使用 FFprobe 校验 MP4、H.264 视频轨、AAC 音轨、1080×1920 竖屏尺寸和 5–120 秒时长。
- 计算本地七牛 ETag、文件大小和 MIME。
- 远端对象不存在时上传；远端对象存在且 Hash、大小、MIME 全部一致时幂等成功。
- 远端对象存在但内容不同或元数据不符时立即失败，禁止覆盖正式版本对象。
- 上传后再次读取七牛元数据并逐项核对。
- 输出动作编码、对象 Key、大小与校验结果，不输出 AK、SK 或签名 token。

数据迁移不得执行网络上传。发布时必须先完成对象上传与验证，再部署引用这些 Key 的后端迁移。

## 6. 数据模型与签名

### 6.1 模型字段

新增：

```text
ActionLibraryItem.video_object_key: CharField(max_length=500, blank=True)
PrescriptionAction.video_object_key_snapshot: CharField(max_length=500, blank=True)
```

字段允许为空，以兼容非视频动作和旧数据。`Prescription.add_action_snapshot()` 必须复制 `video_object_key`。

现有 `video_url` 与 `video_url_snapshot` 暂时保留，供旧数据和 API 兼容使用。对于五个正式运动动作，数据迁移必须：

- 给动作库写入固定 `v1` 对象 Key。
- 按 `PrescriptionAction.action_library_item.source_key` 给全部生效与历史快照写入对应 Key。
- 清除五个动作库记录及其全部处方快照中的测试或旧 URL，确保肩部推举不再回退旧源。

### 6.2 签名服务

新增教学视频专用配置：

```text
MOTION_ACTION_VIDEO_DOWNLOAD_DOMAIN=https://cdn.whestsun.com
MOTION_ACTION_VIDEO_TOKEN_TTL_SECONDS=7200
```

教学视频签名与患者训练录像签名使用同一七牛私有空间和密钥，但配置、调用入口和 TTL 独立。后端启动或签名时必须拒绝非 HTTPS 教学视频域名。

签名服务只接受经过固定动作对象 Key 白名单验证的值。患者当前处方序列化规则：

1. `video_object_key_snapshot` 非空时，动态签名并通过既有 `video_url` 字段返回。
2. Key 为空时，才允许回退旧 `video_url_snapshot`。
3. 不向小程序暴露七牛密钥。
4. 小程序进入说明、预览或摄像页时重新读取当前处方，避免使用已过期缓存 URL。
5. 单个动作签名失败时，当前处方接口仍返回其它业务数据；失败动作返回空 `video_url` 和 `video_unavailable=true`，不得让整个处方接口失败。

医生端动作库与处方序列化也应基于对象 Key 返回“已配置”状态；需要播放教学视频的既有界面继续通过兼容字段获得动态签名 URL，不能因数据库 URL 被清空而显示“无视频资源”。

### 6.3 审核演示清单

新增只读接口：

```text
GET /api/patient-app/demo-motion-videos/
```

接口无需患者 token，只返回固定五个动作编码及其短期签名 URL。它必须：

- 不接受任意对象 Key、动作编码过滤或路径参数。
- 不读取或返回患者、项目、处方、训练记录或绑定信息。
- 按客户端 IP 限制为每分钟最多 60 次，并缓存完整清单响应 60 秒。
- 在配置缺失或签名失败时返回安全错误，不回退长期 token。

## 7. 通用录像资格与训练记录

后端建立唯一的 `OFFICIAL_MOTION_ACTION_SOURCE_KEYS` 正式运动动作集合，动作库、处方、患者录像资格、手工打卡限制、小程序路由和演示清单共同引用，避免维护多份漂移白名单。

将肩部推举专用 `_get_current_shoulder_action()` 泛化为当前处方下的可录像运动动作校验。创建录像会话必须同时满足：

- 动作属于 token 对应患者的当前生效处方。
- 动作编码属于固定五动作集合。
- 处方动作内部类型快照为 `motion`。
- 计划时长为 1–30 分钟。

患者端通用 `training-records/` 接口必须拒绝固定五动作集合中的任何动作，避免绕过录像流程。游戏和其它仍允许手工提交的非录像动作保持原行为。

训练视频合并、七牛发布和 `TrainingRecord` 绑定继续使用现有幂等链路。医生训练追踪页对五个动作统一展示录像状态、播放入口、处理错误和训练健康观察窗口。

## 8. 通用小程序跟练引擎

### 8.1 模块边界

新增 `miniapp/src/pages/motion-training/`，负责：

- 当前运动动作解析。
- 动作说明与双入口。
- 独立教学视频预览。
- 前置摄像头与示范视频画中画。
- 录像计时、暂停与自动结束。
- 五秒分片、压缩、上传队列与缓冲保护。
- 强制补传、失败恢复和完成状态。

从 `shoulder-press` 模块抽取通用纯函数、类型和组件。页面与内部符号使用 `motionTraining` 语义，不复制五套实现。

### 8.2 真实患者流程

1. 当前运动计划中的五个正式运动动作统一显示“开始跟练”。
2. 动作说明页展示名称、动作说明、处方时长和“开始训练 / 动作预览”。
3. 独立预览页静音、自动、循环播放正式教学视频；播放失败可重新获取签名并重试。
4. 训练页以前置摄像头为主画面，左侧显示正计时和剩余时间，右侧显示可收起与恢复的静音示范视频。
5. 当前处方、摄像头和本地存储预检成功后，才创建服务端录像会话并开始计时。
6. 每五秒完成一个录像分片，压缩后后台单并发上传。
7. 切到后台时安全暂停并保存尾段，回到前台后恢复；网络缓慢时按既有高低水位暂停与继续。
8. 达到处方时长自动结束；患者可二次确认后提前结束。
9. 分片全部上传后完成会话；合并和七牛发布成功才生成训练记录。
10. 处理未完成或存在本地待上传内容时，优先进入强制恢复页，禁止开始另一场运动录像。

教学视频是辅助信息。教学视频播放失败不能破坏摄像、录像、分片和恢复状态；但必须明确提示并允许刷新签名重试。

### 8.3 30 分钟容量边界

统一业务边界：

```text
TRAINING_VIDEO_MAX_DURATION_SECONDS=1800
TRAINING_VIDEO_MAX_SEGMENTS=360
TRAINING_VIDEO_MAX_SIZE_BYTES=536870912
```

医生开具正式运动动作时，`duration_minutes` 必须为 1–30。后端在创建会话、接收分片和完成会话时校验计划时长、实际时长、分片连续性和累计字节数。单次会话累计原始分片与合并结果均不得超过 512 MiB；达到上限后拒绝新分片并保留已接收内容供安全恢复或清理。

小程序继续采用约 65 MB 未上传缓冲高水位和约 10 MB 恢复低水位。30 分钟上限不意味着本地同时保存完整 30 分钟录像；已上传分片仍按既有安全所有权规则清理。

### 8.4 审核演示流程

审核演示计划增加五个正式运动动作，并通过只读演示清单获取短期教学视频 URL。它复用说明、预览、摄像布局、画中画、计时和权限引导，但使用独立演示执行器：

- 五个动作统一计时 10 分钟。
- 允许提前结束。
- 只渲染前置 `Camera` 预览，不创建 `CameraContext`。
- 不调用 `startRecord`、`stopRecord`、分片 API、上传 API或完成 API。
- 不创建或保存本地录像文件。
- 不写患者 token、待上传会话、训练记录或本周进度。
- 返回运动计划后只展示本地体验完成状态。

## 9. 升级兼容

现有小程序可能存在肩部推举待上传会话。升级必须保留：

- 旧肩部推举页面路由作为通用页面的兼容入口。
- 旧本地存储 Key 的读取能力。
- 旧会话载荷字段与上传恢复语义。
- 旧强制上传页地址的恢复能力。

新建会话使用通用运动训练命名和存储结构。检测到旧会话时优先恢复、补传和清理，成功后再迁移或删除旧 Key。任何兼容迁移都不能在确认服务端已接收或用户明确放弃之前删除本地录像文件。

后端继续通过既有 `video_url` 响应字段返回新签名值，使旧版小程序在前后端发布窗口内仍可播放肩部推举正式视频。

## 10. AI 分析扩展边界

建立动作编码到分析器的注册表。每个分析器应封装：

- 是否支持指定动作。
- 如何运行推理与规则计算。
- 如何序列化标准、非标准和质量结果。
- 医生端可展示的能力标识。

本期注册表只包含 `motion-resistance-shoulder-press`，继续复用现有 PP-TinyPose 和肩部推举规则，不改变算法结果。其它四个动作的录像可以正常审阅，但创建分析任务必须返回“不支持当前动作分析”，医生端不显示分析入口。

既有 `has_ai_supervision` 是动作库历史业务字段，不作为分析器是否已落地的判断依据。后端和医生端使用注册表计算独立的 `analysis_available` 能力，避免旧字段值导致未实现的动作误显示分析入口。

未来增加动作分析时，只新增分析器并注册动作编码，不修改录像、分片、合并、七牛、训练记录或小程序跟练主流程。

## 11. 异常处理

| 场景 | 行为 |
| --- | --- |
| 教学视频签名失败 | 展示安全错误并允许重试；不输出 Key、token 或密钥 |
| 教学视频播放失败 | 重新读取当前处方并刷新一次签名；仍失败时允许继续录像 |
| 当前处方已更新 | 禁止创建新会话，返回当前运动计划重新选择 |
| 摄像头权限失败 | 禁止开始，提供打开设置与返回入口 |
| 本地空间不足 | 清理可清理文件后重新检测；仍不足则禁止开始 |
| 网络缓慢 | 保留本地分片并在高水位暂停，低水位后恢复 |
| 切到后台 | 安全暂停、保存尾段；回前台后恢复或补传 |
| 分片冲突或缺失 | 保持本地所有权，进入恢复流程，不生成训练记录 |
| 合并或七牛发布失败 | 保留可恢复状态并重试，成功前不生成训练记录 |
| AI 未注册 | 录像与训练记录正常完成，不显示分析入口 |
| 演示清单不可用 | 显示重试提示，不降级为长期签名，不产生真实副作用 |

## 12. 发布顺序

1. 在目标七牛空间执行正式素材上传命令并核对五个远端对象。
2. 部署后端字段、数据迁移、签名服务、演示清单与五动作录像资格。
3. 验证旧版小程序仍能通过兼容 `video_url` 播放肩部推举正式视频。
4. 构建并发布包含通用运动跟练引擎的新版小程序。
5. 本次不移除旧肩部推举路由和本地会话兼容；未来移除必须另行设计并取得用户确认。

上传先于数据迁移，后端先于小程序。任一步失败时不得删除已上传的版本化正式对象；未被数据库引用的对象可以保留待重试，因为固定版本 Key 禁止覆盖。

## 13. 测试与验收

### 13.1 自动化测试

- 五个本地素材映射、FFprobe 校验、幂等上传和远端元数据冲突拒绝。
- 动作库字段迁移及全部生效、历史处方快照回填。
